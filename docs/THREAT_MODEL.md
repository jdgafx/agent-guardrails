# Threat model

What this plugin (agent-guardrails, a Claude Code plugin) is for, what it stops, and what it does not. For how to install and start, see the [README](../README.md); for the demo and the install options, see [ARCHITECTURE.md](ARCHITECTURE.md).

## How it works

Claude Code can run a small script, called a hook, before and after every tool call (reading a file, running a shell command, fetching a page). This plugin is two such scripts, plus the policy and the engine code they use. Before the call, it checks the call against a list of rules and answers **deny** (the call does not run), **ask** (Claude Code asks you first) or **allow** (nothing is printed, and Claude Code's normal prompts still apply, except in bypass mode, limit 5; this is Claude Code's documented behaviour and is not tested here). A deny or ask is logged before the call. After the call, it writes a log line for the call that ran, when the Post script runs and works, and scans the results of every tool that is not trusted for injection phrases (a signal, not a shield: on a hit Claude is told the result is data and you see a notice, and a hit from a tool that reads outside content also marks the session, so that shell, web and MCP steps ask until it ends). A rule that would deny a shell command (Bash, PowerShell or Monitor) asks instead, because shell text can be spelled in ways no rule matches; a file or MCP tool call that names the same thing is still denied. With the opt-in isolation layer on, the Pre script also refuses shell calls while the sandbox settings block is missing or a project setting opens it, and the Post script replaces secrets with a known shape in the output of a successful shell command (the one case where this plugin changes what Claude sees). The scripts are `hooks/pre_tool_use.py` ("the Pre script") and `hooks/post_tool_use.py` ("the Post script"). The plugin needs `python3` on PATH. More detail is in [ARCHITECTURE.md](ARCHITECTURE.md).

Words used below:
- **MCP**: a standard way to plug extra tools into Claude Code. MCP tools are named `mcp__<server>__<tool>`.
- **Vendor folder**: a copy of the engine code (the Python package that makes the decisions) inside the plugin folder, at `vendor/`, so the plugin works with no install step.
- **Data folder**: the folder Claude Code gives the plugin through `${CLAUDE_PLUGIN_DATA}`, outside the plugin folder. The plugin keeps its log (`audit/`), its counters (`state/`) and an optional policy file of your own there. The shipped `policy.json` in the plugin folder always loads first. A `policy.json` in the data folder, and a file named by the `GUARDRAILS_POLICY` environment variable, are **added policy files**: they are merged into the shipped policy and can only add rules or lower the step cap; the one exception is `trusted_tools`, which turns off the injection scan (the log warning and the note to Claude) for the tools it names. A missing or broken added policy file is left out, the shipped rules still apply, and calls no rule matches ask (the full rules are in [ARCHITECTURE.md](ARCHITECTURE.md), "Trust boundary"). The [GLOSSARY](../GLOSSARY.md) defines the other terms.
- **Decision line and result line**: the two kinds of log line. A decision line is written when a call is denied or asked (not for an ask caused by an internal error, and not when the decision memo cannot be written; see "Limits of the log"). A result line is written after a call has run.
- **Guard paths**: the plugin folder, the data folder and the file named by `GUARDRAILS_POLICY`. The plugin protects them (limit 7).
- **State files**: small files in the data folder where the plugin counts calls, remembers its decision for the second hook (`<sid>.calls`, `<sid>.decisions`) and keeps the session mark (`<sid>.taint`, see limit 2). Pre reads the size of the mark file on every call.
- **Flagged result and marked session**: a result is flagged when the injection scan finds a marker in it. A session is marked when a flagged result came from a tool that reads outside content (an `untrusted_tools` pattern names it: WebFetch, WebSearch, MCP read tools). While it is marked, every tool except the local-file ones asks.
- **Step cap**: after 200 tool calls in one session (every call counts once the rules have decided it, whether or not a rule matched it), a call that matches no rule gets `ask`. A new session has a new id and starts at zero. (If Claude Code sends no session id, all calls share one counter file, so after 200 calls in total, across all sessions and days, every call that matches no rule asks; see ARCHITECTURE.md, "Audit and state".)

## What it protects

- Your secrets, as far as a tool call names a listed credential file or folder (`.env` files, keys, cloud, SSH, git and package-registry credentials) in any field of its input (denied) or as a word of a shell command (asked).
- Shared and live systems (git history, production, packages, clusters, other people's inboxes), for the listed commands and spellings only ("Gaps in the rules" lists what is missed).
- Your time: a runaway agent that loops. The cap is soft (a question after 200 calls, not a stop).

## Who or what to worry about

1. **A confused agent.** It tries to do the task and does something destructive (`rm -rf`, a force push). This is the case the design assumes (see "Design stance").
2. **A prompt injection.** Text in a web page or tool result tries to give the agent new orders.
3. **A mistake in the guard itself.** A crash, a bad policy file, a full disk.
4. **An agent that edits the guard.** On purpose after an injection, or by accident while it tries to get past a false positive.
5. **Hostile content in a repository you open.** A repository can ship files and Claude Code project settings of its own. Whether those settings can set `GUARDRAILS_POLICY` (an added policy file, which can only add rules, and can set `trusted_tools` to turn off the injection scan of Bash, Read and Grep output) or switch the plugin off was not checked here; see limit 7.

This plugin does not try to stop a skilled human attacker who already has a shell on your machine.

## What each control covers

| Threat | Control | How well |
|--------|---------|----------|
| Agent reads `.env` or a key | `deny-env-files`, `deny-key-files`, `deny-credential-dirs` | Denies reads and writes of the listed files and folders named in any field of a file or MCP tool input (dict keys and lists too; the listed text fields of built-in tools, such as the Edit `new_string`, the Write `content`, the Grep `pattern` and the SendMessage `message`, are skipped; see "Gaps in the rules" for the list and its limits) and asks, with a log line, when any word of a shell command names one (`cat .env`, `cp .env x`, `tar czf k.tgz ~/.ssh`). Paths are cleaned up first (`/./` and `//`). Does not stop content search (the Grep tool's too), globs, environment variables, or the forms in "Gaps in the rules", secrets; with isolation on, the sandbox blocks the shell forms for the listed files ("Isolation (opt-in)" under "Gaps in the rules"). |
| Agent reads a listed secret file from the shell without naming it (`cat .e""nv`, a glob, a link) | Opt-in isolation: Claude Code's sandbox with a generated block, `isolation-not-active` (Pre), the link check (Pre), shaped-secret redaction (Post) | Off by default. When on and the block is in force: the listed files in the project and directly in `~` and `~/.config` are unreadable to Bash, PowerShell and Monitor commands (tested live, "What holds each threat" below). Not covered: environment variables, the Grep tool and MCP tools, old copies in git, files elsewhere, key files. The check that the block is in force sees the project settings files only. |
| Agent rewrites shared git history | `deny-force-push` | Asks (rule `deny-force-push`) on `--force`, `--force-with-lease`, `-f` and `+branch` (a leading `+` is git's way of forcing a push) when `push` follows `git`, with option words allowed between them (`git -C repo push --force` asks), anywhere in the command (`cd r && git push --force` asks). The barrier is a GitHub ruleset on the branch ("What holds each threat" below). Misses quoted or hidden spellings: see "Gaps in the rules", command spellings. |
| Agent publishes or deploys | `ask-*` rules | A human sees the command first, but only for the listed commands, with option words allowed before the subcommand (T-006): `git push`, `rm -r`, `git reset --hard`, `git clean -f`, `terraform apply` and `destroy`, `kubectl apply` and `delete`, `vercel --prod` and `--target=production`, `npm`/`pnpm`/`yarn publish`, `twine upload`, `cargo publish`, `uv publish`, `gem push`, `gh pr merge`, `gh release create`, `docker push`, `helm install`, `upgrade` and `uninstall`, `find -delete`, a `python -c` one-liner that deletes files, `aws s3 rm`, `cp`, `mv` and `sync` and `aws` operations (the word after the service name, as in `aws ec2 terminate-instances`) starting `delete-`, `put-`, `create-`, `update-` or `terminate-`, and MCP tools with a write word (`send`, `delete`, `post`, `pay`, `charge`, `transfer`) at the start of a word of the tool name (`mcp__gmail__send_email`, `mcp__x__bulkDelete` and `mcp__x__make-payment` ask; `mcp__x__get_posts`, `mcp__x__list_payments` and `mcp__x__resend` do not). `policy.json` is the full list. Other commands and spellings are not covered: see "Gaps in the rules". |
| Agent touches production config | `deny-prod-config` | Path based. Over-matches (any `prod` folder below the project folder or outside it); a project that sits under such a folder is not hit; see "Known false positives". |
| Internal error or bad input in the hook | Fail safe (ask), with the rules run first | Tested with broken JSON, a missing `vendor/` folder, a data folder that is a file or read-only, an unset data folder and a broken added policy file. A deny stays a deny in all of these (a Read of `.env`, tested), and a shell command that names `.env` stays an ask; a call no rule matches asks. A broken added policy file is left out, the shipped rules still apply, and the ask names the file and the error. Every policy file is checked against the whole schema, so a text `except`, a misspelled key or a missing `step_cap` is an error, not a silent weakening. A broken or missing shipped policy still asks on every call, except the denies on the guard's own files. |
| Hook cannot start (no `python3`), crashes outside its handler, or times out | `"onFailure": "block"` in `hooks.json` (Claude Code 2.1.295+) | On older versions the call probably goes ahead (per the release notes; not tested; see limit 9). Tested: with no `python3`, the hook command (the shell command in `hooks.json`; the script never starts) exits with a code other than 0 or 2 and prints nothing (0 is success and 2 is the code a hook uses to block a call, so any other code means the hook failed). That Claude Code then blocks the call comes from its release notes (2.1.295), not from a test here. A timeout is not tested live. |
| Huge command that makes the regex scan slow | `oversize-command` ask over 20000 characters, regexes rewritten to avoid the slow case seen on a 60 KB `rm` input | A long command that also holds a deny pattern gets ask, not deny. |
| Agent loops forever | Step cap (ask after 200 calls in one session) | Soft cap. Counts calls, not cost. The counter file has no lock, so parallel calls can share a step number. |
| Injection in a web page | Scan, tell Claude, mark the session (`ask-after-injection`) | **Looks for six known phrases in the output of every tool not trusted, tells Claude and you on a hit, and makes shell, web and MCP steps ask for the rest of the session after a hit from an outside-source tool; stops none by itself, and does not see a reworded one.** |
| Need to see what happened | Redacted audit log | Partial. An allowed call has no line until it finishes, an internal-error ask is logged only when the data folder can be written, and the agent can edit the files (see "Limits of the log"). |
| Agent edits the guard's rules, counter, log, scripts or Claude Code settings | `deny-guard-files`, `ask-guard-paths`, `ask-claude-settings`, add-only policy files | The write tools cannot change the guard's files, and an added policy file cannot loosen a shipped rule. A Bash command that does not name a guard path as an absolute or `~` path can still write them. See limit 7. |
| Hostile content in a repository you open (threat 5) | `ask-claude-settings` for write-tool edits to the four settings files | Partly. Settings that ship inside the repository are not checked here. See limit 7. |
| A shell started through a tool not named `Bash` | The path rules | Partly: PowerShell and Monitor are shell tools and ask when the whole command string matches a path rule (not word by word, as Bash is); for another tool name the strings are matched whole against the path rules and denied, with no command rule. See "Gaps in the rules", other tools, and limit 4. |

## What holds each threat

Each cell of the first table uses these terms.
- **hook deny**: Pre refuses the call. It applies to a call whose path field names the thing (the Read, Edit, MultiEdit, Write, NotebookEdit, Grep and Glob tools, and MCP tools). Text fields such as Write `content` are not checked.
- **tripwire deny**: with isolation on, Pre refuses every shell call until a setting is fixed.
- **ask + log only**: Pre asks you and writes a log line. The shell text was matched, and another spelling would not be.
- **sandbox**: Claude Code's sandbox, with this plugin's block, stops it however the command spells the name. File names are case-sensitive there: `.ENV` is not hidden.
- **redacted**: Post replaces known key formats in shell output.
- **GitHub ruleset**: GitHub refuses it on the server.
- **not held**: no part of this plugin or the sandbox stops it.

Turn isolation on if its costs suit you (see "Isolation (opt-in)" in [ARCHITECTURE.md](ARCHITECTURE.md#isolation-from-the-users-side)); we recommend it. It is off by default because of those costs.

The isolation-on column assumes the block is in the project's settings files and Claude Code started in the project folder. `--settings`, `--add-dir`, user settings and managed settings can open the sandbox without Pre seeing it. Write folders and hosts that you want in every project go in your user settings (`~/.claude/settings.json`, where lists merge with the project's); Pre cannot see them there. "Not held" for a command means this plugin has no rule for it (the doc test checks every quoted command against the shipped policy), and Claude Code's own prompts still apply. The isolation-on column comes from real `claude -p` sessions (`tests/live/t014_probe.py`, see "Tested on" under "Isolation (opt-in)" in [ARCHITECTURE.md](ARCHITECTURE.md#tested-on)). The sandbox rows for a write outside the project, a file in `.git/hooks` and a rewrite of the project's settings were run live on 2026-11-06 (Claude Code 2.1.319, steps 45 to 47 of the same script): each write was refused with "Read-only file system". Step 47 shows that only when it runs alone; in the script's one session after step 46, the `cd` of step 46 carries over and step 47 writes a different file, so the script's case T018-47 does not test it yet. The Grep tool row holds only when a session turns that tool on; by default on Linux and macOS the search runs as Bash `grep`, which the sandbox covers.

**Force pushes.** The barrier for a force push is on the server. A GitHub ruleset on your default branch with "Block force pushes" and "Restrict deletions" refuses every spelling of a force push and of a branch delete (see GitHub's documentation page "Creating rulesets for a repository", https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository). It holds only while the agent's GitHub login cannot edit rulesets: a repository admin can delete a ruleset (`gh api -X DELETE repos/<owner>/<repo>/rulesets/<id>` has no rule here) and then force-push. Give agent sessions a token without admin rights on the repository. The default branch of this repository has such a ruleset.

**What an ask does in each mode.** An ask stops the call until someone answers. Where nobody can answer (`claude -p`), the call is refused. The two interactive results below were seen once each, with a hook in a `--settings` file and a `Bash` command, not with this plugin and not with other tools.

## Gaps in the rules

These are the gaps behind the table rows above that point here. Each was run against the shipped `policy.json` on 2026-11-05, and the cases are kept as a test (`tests/unit/test_t013_doc_gaps.py`, which records today's behaviour: when a fix changes a case, update the test and this text together). Where a gap has a fix that is written down but not built, the work item is named (see the start of "What it does NOT cover").

**Secrets (T-008 built; what is left).**
- Not stopped by the rules (these forms are stated once as limits; the rules match text, see limit 4). With isolation on, the sandbox blocks the shell forms in this list for the listed files; "Isolation (opt-in)" below says which forms remain:
  - Searching file contents (`grep -r API_KEY .`, `grep -r AWS_SECRET ~`, the Grep tool with `path` on a folder), and any command that reaches a file without writing its name: a parent folder, a shell glob (`cat config/*`, `cat .n*rc`), a built name (`f=.e; cat ${f}nv`), a bare name after `cd` into a folder that is not listed (`cd ~/.config/gh && cat hosts.yml`), a symbolic link made before the call.
  - Secrets in environment variables (`env`, `printenv`).
  - A name glued to other characters (`curl -d @.env.production`), a Grep `glob` that does not spell the name (`*`, `{.env,x}`), an encoded or decorated URI (`%2Eenv`, `?x=1`), and a name relayed over two calls (written to a file in one call, read in the next).
  - Other credential stores: credential files not on the list (`~/.kube` and `~/.docker` other than their config files, and any store not named in `policy.json`).
- The listed names are the patterns of `deny-env-files` (`.env*` and `*.env`, with `*.example`, `*.sample` and `*.template` excused), `deny-key-files`, `deny-credential-dirs` (`~/.aws`, `~/.ssh` and `~/.config/gcloud` as folders and everything in them, `~/.kube/config`, `~/.docker/config.json`, `.netrc`, `.git-credentials`, `.npmrc`, `.pypirc`, `gh/hosts.yml` and `application_default_credentials.json`) and `deny-prod-config` in `policy.json`. A Bash command is split into words, and each word is matched whole. The split happens at white space and at `; & | < > = ( ) " '` and the backtick. Other characters do not split a word, so a name glued to one of them is a different word. The word in `curl -d @.env` is `@.env`: the `*.env` pattern matches it and the call asks. The word in `curl -d @.env.production` is `@.env.production`: neither `.env*` nor `*.env` matches it, so the call is allowed. The same holds for `scp host:.env.local .` and `git show HEAD:.env.production`.
- Every string of a tool input is matched whole against the path rules, at any depth and inside lists, dict keys included, except the text fields of built-in tools (Bash `description`, Write `content`, Edit `old_string` and `new_string`, MultiEdit `edits`, NotebookEdit `new_source`, Grep `pattern`, WebFetch `url` and `prompt`, WebSearch `query`, Agent and Task `prompt` and `description`, TodoWrite `todos`, AskUserQuestion `questions`, ExitPlanMode `plan` and `allowedPrompts`, ToolSearch `query`, SendMessage `message` and `summary`, PushNotification `message`, TaskCreate and TaskUpdate `subject`, `description`, `activeForm` and `metadata`, CronCreate `prompt`, Skill `args`; the whole input of StructuredOutput). So the Grep `glob` and `path` fields, a directory such as `Read ~/.ssh`, and an MCP field with any name are checked. The table lists the built-in tools seen in the tool schemas of Claude Code on 2026-11-05; it is not a promise about every tool. Two limits: a built-in tool missing from the table, or a prose field added to one later, is checked in full, so a note that names `.env` or a production folder is denied (a visible deny with the rule's reason, never a silent allow); and a path field added later inside one of the skipped fields would not be seen.
- Paths are cleaned up before matching: each string is tried as written, with `~` expanded, and with `/./`, `//` and a trailing `/` removed, so `~/.aws/./credentials` and `~/.kube//config` are denied (asked, in a shell command). Symbolic links are not resolved.
- Environment variables have no fix in the rules (limit 8). With isolation off, the shell limits above stay limits: the control for them is the opt-in isolation layer below, or a container or a separate user with no access to the secrets (limit 4).

**Isolation (opt-in; T-014 built).**
- What it is: `"isolation": true` in an added policy file turns it on (no file can turn it off). The plugin ships a settings block for Claude Code's Bash sandbox, generated from the `match` globs of `deny-env-files` and `deny-credential-dirs`; the user copies it into the project's `.claude/settings.local.json`. The sandbox then hides those names from Bash, PowerShell and Monitor commands: anywhere in the project, and directly in `~` and `~/.config`. Pre denies a shell call (rule `isolation-not-active`) when the block is not in force in the project settings files or a project setting opens the sandbox (`sandbox.filesystem.allowWrite`, `permissions.additionalDirectories`, `sandbox.network.allowedDomains`, a `WebFetch(domain:...)` allow rule, an `Edit` allow rule), denies a file tool that opens a listed file through a symbolic link, and Post replaces secrets with a known shape in the output of a successful shell command.
- Blocked, tested live on Claude Code 2.1.318 and 2.1.319 (`tests/live/t014_probe.py`): a bare name after `cd` into an unlisted folder, a shell glob, a built name, a parent folder (`grep -r AWS_SECRET ~`, `tar cf - .`), a name glued to other characters, a name relayed through a file, a link made in the shell, a hard link, a call sent with `dangerouslyDisableSandbox`.
- Still readable with isolation on, each tested at its stated result: environment variables (`printenv` shows a secret with no known prefix; one with a known prefix is replaced only if the command exits 0); the Grep tool when a session turns it on, and MCP servers (they run outside the sandbox); a listed name in a folder outside the project and outside `~` and `~/.config`; old copies in git (`git show HEAD:.e""nv`); key files (`deny-key-files` is not in the block); the output of a command that fails, of a command whose output is large enough to be saved to a file, and of a background command.
- Late files: the sandbox lists the files a `denyRead` pattern matches when each command starts, so a secret created while a shell command is already running is readable by that command, and the next command hides it. For a file pattern (`.env*`) the late file leaks. For a folder pattern (`~/.aws`) a late file in a folder that already existed stays hidden, and only a folder made late leaks. Claude Code 2.1.319 on Linux, tested 4 of 4 each way; it has no re-scan setting.
- The check that the block is in force is a tripwire, not a barrier. Pre cannot see managed settings, a `--settings` flag, `--setting-sources`, `--add-dir` or a user settings file (where extra write folders and trusted hosts belong; they then apply to every project), so a setting there can weaken the block unseen. In bypass mode the agent can edit the project settings file with the Edit tool (limit 5); an edit that loosens the block trips the check on the next shell call.
- The costs that keep it opt-in (ssh and git over ssh, stored https credentials, tools that read `~/.ssh` or a hidden `.npmrc`, user namespaces, one-time AppArmor step on Ubuntu, a copy of the block per project, 0.15 to 1.3 seconds more per command) are in [ARCHITECTURE.md](ARCHITECTURE.md), "Isolation (opt-in)", "Why isolation stays opt-in".

**Command spellings (T-006 built; what is left).**
- Fixed: the command rules accept option words between the program and its subcommand. An option word starts with `-` (for `cargo`, also `+`, as in `cargo +nightly publish`), may be followed by one value word that does not start with `-`, never crosses `;`, `&`, `|` or a line break, and at most 8 may sit between the program and the subcommand. This holds for every command rule that has a subcommand: `git`, `kubectl`, `terraform`, `npm`, `pnpm`, `yarn`, `cargo`, `uv`, `twine`, `gem`, `gh`, `docker` and `helm`.
  - `git -C repo push --force`, `git -c key=value push -f`, `git --no-pager push -f` and `git --git-dir=x push -f` ask under the force-push rule.
  - `git -C repo push`, `git -C repo reset --hard`, `git reset HEAD~1 --hard`, `kubectl -n prod delete pod x`, `kubectl --context prod apply -f x`, `terraform -chdir=infra apply`, `npm --tag x publish`, `pnpm -r publish`, `yarn --cwd x publish`, `cargo +nightly publish`, `uv --directory x publish` and `twine --verbose upload d` ask.
  - A short force flag now ends at white space, `;`, `&`, `|`, `)` or the end of the text, so `git push -f;echo` and `git push -f|cat` match the force-push rule (before, only the plain push rule matched them).
  - `vercel --target=production` asks, as `vercel --prod` does.
- The price: the rules cannot tell an option's value from the subcommand, so `git --no-pager log --grep push` asks, although it only reads (and `aws s3 --profile cp ls` asks for the same reason).
- Still missed (these forms are out of scope and are stated here once; the rules match plain text, see limit 4):
  - Quoting or escaping of the program, the subcommand or a flag: `"rm" -r x`, `rm "-rf" build` and ``git "push" -f`` are allowed with no ask. `git push "--force"`, `git push "-f"`, `git push '--force'` and `bash -c "git push -f"` ask under the plain push rule.
  - A flag hidden in a variable, an alias or a line continuation (`F=--force; git push $F`, `alias gp='git push -f'; gp`, a backslash before a line break): ask, not deny.
  - A flag after a redirection (`git push -f>/dev/null`, `git push origin main 2>&1 --force`): ask, not deny.
  - `vercel` and `--prod` on different lines (`vercel` then a line break, then `--prod`): allowed.
  - More than 8 option words between the program and the subcommand: allowed.
  - An option value with a space in it, quoted or escaped: the value is read as two words, so `git -C "my repo" push --force` and `git -C my\ repo push --force` are allowed with no ask.
- The fix is a change to the regexes in `policy.json`. A shell parser is not planned: an earlier parser attempt did not converge in three rounds, and the regex change needed no engine change.

**Commands with no rule (T-006 added some).**
- Now ask: `gh pr merge`, `gh release create` and `gh release delete`, `gh repo delete`, `docker push` (also `docker image push`, `docker manifest push`, `docker compose push`, `docker compose -f prod.yml push`), `helm install`, `helm upgrade`, `helm uninstall` (also `helm delete` and `helm rollback`), `git clean` with a force flag (`git clean -fdx`; a dry-run flag anywhere excuses it, so `git clean -n`, `git clean -n -f` and `git clean -df --dry-run` do not ask), `find` with `-delete` or `-exec rm`, a `python -c` one-liner that names `rmtree`, `unlink`, `rmdir`, `removedirs` or `os.remove`, `aws s3 rm`, `cp`, `mv` and `sync`, and any `aws` operation (the word after the service name, as in `aws ec2 terminate-instances`) that starts with `delete-`, `put-`, `create-`, `update-` or `terminate-`. Read commands such as `aws s3 ls`, `aws lambda get-function --function-name create-order` and `aws cloudformation describe-stacks --stack-name delete-me` (a value, not the operation),  `gh pr view`, `helm list`, `docker build .` and `find . -name x` are allowed.
- Still no rule: `rm -f`, a script that deletes files (`python3 script.py`), `aws s3 rb` and other `aws` operations outside the list above, `kubectl patch` and `scale`, `gh api -X DELETE`, `git branch -D`, `docker buildx build --push`, and MCP tools such as `push_files`, `merge_pull_request` or `create_issue`.
- MCP tool names are read at the start of a word of the tool part of the name (after the server name): after `_` or `-`, at a change from lower to upper case (`bulkDelete`, `createPost`) and at the start. `send` and `delete` ask; `post`, `pay`, `charge` and `transfer` ask unless the name starts with a reading word (`get`, `list`, `read`, `fetch`, `search`, `query`, `find`, `describe`, `view`, `show`, `check`, `count`, `browse`, `lookup`) followed directly by that write word, so `get_posts`, `getPost` and `list_payments` are allowed, and `find_and_pay`, `fetch_and_post` and `getAndPost` ask. A write word with no word break (`createpost`, `resend`) is not seen. The server name does not count (`mcp__my_pay__list` and `mcp__my_sender__list` are allowed). **Known limit:** the reading word is checked once, at the start of the tool part of the name. When a name starts with a reading word and a write word comes directly after it, every later write word in the name is excused too, so `mcp__x__get_payment_then_transfer` and `mcp__x__list_payments_and_charge` are allowed, although they move money. The rule does not ask on them.

**Your own policy file (built in T-007).**
- A policy file of your own (in the data folder, or named by `GUARDRAILS_POLICY`) is added to the shipped one and can only add (`trusted_tools` is the one key that turns something off: the injection scan, with its log warning and the note to Claude, for the tools it names). Rules and fixes added to the shipped file later (T-006, T-008) reach every user. The price: you cannot loosen a shipped rule from your own file (the false positive on `git commit -m "fix production/config"` stays an ask unless you edit the shipped file by hand).

**Other tools (no fix written down).**
- Command rules and the word-by-word split read only a tool named exactly `Bash`. A shell started through any other tool name (a different shell tool, or an MCP server that runs commands) gets no command rule. The strings of every other tool are matched whole against the path rules, so `cat .env` sent through such a tool is denied (it ends in `.env`), and a string that only ends in `.env.local` is allowed (the whole string does not match). PowerShell and Monitor are shell tools: a path rule that matches their whole command string asks, but their words are not split as Bash words are, and they get no command rule. Tested with the tool names `PowerShell` (asks), `Shell` and `bash` (deny).

## What it does NOT cover

Limits 1 to 4, 7 and 8 apply to any setup. Limit 5 needs bypass mode, which a user must switch on. Limit 6 needs `claude -p`. Limit 9 applies only to Claude Code older than 2.1.295 (check with `claude --version`).

The text gives the aim of each fix, not its design. Where a gap has a fix that is written down but not built, the text says "Fix not built yet" and gives the number of the open work item (the project's own numbering; the work items are not in this repo): no work item is open now. T-006 (command spellings and missing commands), T-007 (the policy files can only add, `trusted_tools` aside; a deny stays a deny; the guard's files are protected from the write tools), T-008 (secrets named in any field, more credential files) and T-009 (the injection scan: every tool not trusted, failed calls, a time limit, error asks logged) and T-014 (opt-in isolation for shell reads of the listed secret files) are built; what they leave is listed under "Gaps in the rules" and limit 7. A broken or missing shipped policy still turns a would-be deny into an ask (except the denies on the guard's own files); the built-in minimum deny list that would cover it is not built and has no work item.

### 1. No spend cap
The plugin counts calls. It does not know what a call costs. A loop of expensive calls under the cap can still run up a bill. Set limits at your model provider.

### 2. The model can still follow bad instructions inside allowed tools
Prompt injection is not solved here. The scan is a signal, not a shield: on a hit the plugin tells Claude, in the same step, that the result may hold text written to give it orders and is data, not instructions from you; you see a one-line notice in the window; the result is not removed or changed; and the log line carries `warned`. The note is advice the model can ignore. What holds the step that sends data out is the session mark (below). It looks for six known phrases in the output of every tool you have not listed in `trusted_tools`, failed calls included (WebFetch, WebSearch and MCP read tools stay scanned even if a pattern trusts them). So the output of `curl` or `gh issue view` in Bash, a file read with the Read tool, a subagent's answer, and a tool called `mcp__target__x` are all scanned. It reads the text values of the result: dict keys, numbers and long runs of base64 (image data) are skipped, the text gets NFKC, invisible format characters (zero-width space, soft hyphen) are removed, and white space and the two-character escapes `\n`, `\r` and `\t` collapse to one space. Only the first 200000 characters of a result are scanned. When text was cut, the result line says `scan_truncated: true`. One 3-second timer covers the whole scan (not on Windows, or off the main thread). What it misses, stated once: a phrase in other words or another language, look-alike letters from other scripts (Cyrillic `о`), HTML entities, base64, `\uXXXX` escapes inside text, hyphens or underscores between the words, a gap over 60 characters in `exfil-request`; invisible characters outside the removed class (variation selectors, U+034F, the Hangul fillers, U+2800), which can split a word; images and audio (a model can read text in an image); and a result nested deeper than Python's JSON parser accepts (about 100000 levels), which makes the Post script exit 1 with no line. Instruction files that Claude Code loads by itself (for example a `CLAUDE.md`) and the result of a background agent or shell that arrives as a notification are not scanned, because no tool call carries them. Every tool is scanned, so reading a security test or a doc about injection gives a warning, and its excerpt (up to 80 characters, redacted) can come from a local file; `exfil-request` needs a verb, a determiner and a secret word in a row, so ordinary login code no longer warns. `trusted_tools` in your own policy file turns the scan off for a tool: it is the one key that turns something off, and what it turns off is the log warning and the note to Claude, never a deny or an ask. Phrasing is open-ended: no marker list can be complete, so a phrasing that passes is a stated limit of the scan, not a bug. If the injected order then asks for a tool call, the policy rules still apply to that call. They judge the action, not the text that caused it. That stops only orders written in a listed spelling: the rules match text, and an injected order can ask for an encoded or indirect command (see limit 4). Isolation is the control against a determined injection. This plugin's opt-in isolation blocks shell reads of the listed secret files only; for everything else use a container or a separate user with no access to your secrets.

**The session mark.** When the flagged result came from a tool that an `untrusted_tools` pattern names (WebFetch, WebSearch, an MCP tool whose name holds read, get, fetch, search, list, query, browse, scrape or download), Post writes `state/<session id>.taint`. While that file is there and not empty, Pre asks (rule `ask-after-injection`) for every tool except these: Read, Write, Edit, MultiEdit, NotebookEdit, Grep, Glob, TodoWrite, TaskCreate, TaskUpdate, TaskGet, TaskList, TaskOutput, TaskStop, ToolSearch, AskUserQuestion, EnterPlanMode, ExitPlanMode, StructuredOutput, SubagentHandback and ScheduleWakeup. The check reads the tool name only, never the command or the address, so a respelled command, an encoded payload or a new host gets the same answer, and a tool nobody listed asks. WebFetch asks on every call, also for a site fetched before, because the address itself can carry data out. Agent asks because a subagent runs work the marked session hands it. A subagent's own calls carry the parent's session id and an `agent_id` (seen live on Claude Code 2.1.319, `tests/live/t033_evidence.txt`), so a flag in a subagent marks the parent session too. A shipped rule that also asks keeps its own id, and a deny stays a deny. An unreadable mark makes every call ask (`guardrails-error`). The mark ends with the session id (`/clear` gives a new one, seen live on Claude Code 2.1.319); you can end it at any time by deleting the file the notice names. Claude cannot clear it: the write tools are denied on the data folder, and a shell command that names the file asks. The limits, each accepted:
- **A signal, not a barrier.** The mark follows the six-marker scan. A reworded, translated or encoded injection is not flagged and does not mark the session.
- **Outside content through a tool `untrusted_tools` does not name.** `curl` output in Bash, a file from a cloned repository, a subagent's answer, or an MCP tool whose name has none of the listed words (`mcp__jira__issue`) gets the note and the notice but does not mark the session. To make such a tool mark, name it in `untrusted_tools` in your own policy file.
- **WebFetch hands the hook a summary, not the page.** In real transcripts its result is a small model's answer about the page (a 106 KB page came back as a 5 KB answer). The scan sees that answer, so an injection the small model rewords or drops is not flagged. MCP fetch tools pass the raw text.
- **Calls in the same batch.** Calls Claude made in parallel with the flagged call were decided before its result came back, and are not asked.
- **A Post failure loses the mark.** If the Post script crashes before it writes the mark, or runs past its 10-second limit, no mark is written. A failed mark write is still named in the notice, and the note to Claude is still printed.
- **Headless runs stop.** In `claude -p` nobody can answer an ask (limit 6), so a marked session cannot run shell, MCP, web or Agent calls.
- **Prompt fatigue.** A person asked many times may answer yes without reading. The reason text names the flagged tool and how to clear the mark.
- **Bypass mode.** A hook's ask still showed a prompt in interactive bypass mode when tested (limit 5); that is the only thing that holds the mark there.
- **New session ids carry the old context.** `--fork-session`, and possibly `--resume` or `--continue`, start a new session id while replaying the transcript that holds the injected text, so the new id is unmarked. Carrying the mark across would need a SessionStart hook.
- **Files written while marked run later.** Write and Edit stay free, so a marked session can write files that run outside it (`.git/hooks/*`, `~/.bashrc`, `package.json` scripts, a `Makefile`; limit 3). Where isolation is on, its write limits hold the ones outside the project.
- **Session id missing.** A call with no session id uses `unknown`, shared by all such calls, as the step counter does.

### 3. Attacks outside Claude Code
Hooks only see Claude Code tool calls. They do not stop the model from saying things, and these are out of reach:
- A dependency you install that runs code at install time.
- A script the agent writes and then runs. The hook sees `python script.py`, not what is inside it.
- Anything you do in your own terminal.
- Files the agent writes that other programs run later, outside Claude Code and with no hook involved: `.git/hooks/*`, shell start-up files such as `~/.bashrc`, `package.json` scripts, a `Makefile`, `.github/workflows/*`. No rule covers them, so one session's injection can leave code that keeps running after the session. Calls made by subagents do reach these hooks, with the parent's session id (seen live on Claude Code 2.1.319).

Use a container or a separate user with no access to your secrets for these (limits 2 and 4).

### 4. Pattern rules are not a sandbox
Rules match text. A determined agent or attacker can get around them: build a path in a variable, encode a command, read a file through a program the rules do not know. The rules stop the listed commands and file names in the listed spellings. For hard isolation, use a container or a separate user with no access to the secrets; this plugin's opt-in isolation layer covers shell reads of the listed secret files only (see "Isolation (opt-in)" under "Gaps in the rules"). Command rules read only a tool named `Bash`: a shell started through any other tool (a different shell tool, or an MCP server that runs commands) gets no command rule at all. No fix is written down for this. Claude Code's own Bash sandbox is another layer: the isolation layer uses it for reads of the listed secret files (tested live), and its other defaults were not tested here (see "How this relates to Claude Code's own controls" in [ARCHITECTURE.md](ARCHITECTURE.md)).

### 5. Bypass mode
Claude Code can run with permission checks off (the `--dangerously-skip-permissions` flag, or the `bypassPermissions` mode). In interactive bypass mode a hook's `ask` still stopped the command and showed a prompt (tested 2026-11-06 on Claude Code 2.1.319 with one stub hook and one harmless command; "What holds each threat" above). In `claude -p` with bypass mode, a hook's `ask` and `deny` both stopped the call (the same version). A Claude Code upgrade can change this. A shell read of a listed secret is only asked about, so it is held by the answer of the person at the keyboard, and by isolation. Every `ask` is only as strong as that answer: the `ask` rules, the fail-safe `ask` on internal errors, the `oversize-command` ask (padding a command past 20000 characters turns a deny into an ask, and the person can answer yes), `ask-guard-paths`, `ask-claude-settings` and the step cap. A full disk or an unwritable data folder no longer turns a deny into an ask (the rules run before the data folder is touched). `ask-guard-paths` and `ask-claude-settings` are asks too, so they are weak in that mode. Put what must never run in Claude Code's own `permissions.deny` as well ("How this relates to Claude Code's own controls" in [ARCHITECTURE.md](ARCHITECTURE.md); check its release notes first).

### 6. Headless runs
In `claude -p`, nobody can answer an ask, and the call is refused. This was seen in a real `claude -p` run (the log under "Log from one live session" below, 2026-10-25: no result line for the asked call) and in a stub-hook run on Claude Code 2.1.319 in the default, acceptEdits, auto, dontAsk and bypassPermissions modes (the marker file the command would have made was not created). The session went on with the next call. A `PermissionRequest` hook or `--permission-prompt-tool` can approve the call instead. No automated test covers it; the runs were by hand, on one version, with Haiku.

### 7. The agent can change the guard itself
The guard is made of files, and the agent can write to them. Some hold its rules and records: the shipped `policy.json`, the added policy files (in the data folder, or the file named by `GUARDRAILS_POLICY`), the step counter (`state/`) and the log (`audit/`). Others decide whether the guard runs at all: the two hook scripts (`hooks/pre_tool_use.py`, `hooks/post_tool_use.py`), the copy of the engine code (`vendor/`), the hook list (`hooks/hooks.json`), and Claude Code's own settings files, where plugins and hooks are switched on and off.

Four things are built and tested (T-007), and they hold for every input of their kind:
- An added policy file can only add rules or lower the step cap; its one exception is `trusted_tools`, which turns off the injection scan (the log warning and the note to Claude) for a tool, never a rule. It can never remove or loosen a shipped rule, however it was written, so replacing or deleting it does not switch the shipped rules off.
- The write tools (Write, Edit, MultiEdit, NotebookEdit) and any MCP tool are denied on the plugin folder, the data folder and the `GUARDRAILS_POLICY` file (`deny-guard-files`). Paths are compared after `~`, `..` and symbolic links are resolved, so a link in the project that points into the data folder is caught. Claude may not edit your policy file for you either: edit it yourself. The Read tool is not affected, so reading the log stays allowed.
- A deny stays a deny when the guard has trouble (threat 3 above).
- A write tool asks before it changes `.claude/settings.json` or `.claude/settings.local.json` in the project, in your home folder or in `CLAUDE_CONFIG_DIR` when that is set (`ask-claude-settings`), because those files can switch the plugin off.

**The limit, stated first.** A shell command can write a file in many ways: a redirect, `sed -i`, `python3 -c`, `cp`, `tee`, a path built in a variable, a relative path after `cd`. Matching on the command text can never catch all of them, and the plugin does not try. A Bash command asks (`ask-guard-paths`) only when it names a guard path as an absolute or `~` path, for example `tail ~/.claude/plugins/data/agent-guardrails/audit/x.jsonl` or `sed -i s/deny/ask/ /opt/agent-guardrails/policy.json`. That is a tripwire, not a barrier, and the set of forms it checks is closed. These are allowed, and tested as allowed: `rm "$CLAUDE_PLUGIN_DATA"/state/s.calls`, `cd ~/.claude/plugins/data && rm agent-guardrails/policy.json`, a guard path with a space, a quote or a backslash in it (the command is split into words there), a glob such as `~/.claude/plugins/data/*/policy.json`, and a parent folder such as `mv ~/.claude/plugins/data /tmp/x`. A word with a NUL byte cannot name a file and is skipped, so it never turns a deny into an ask. A Bash write that never names a guard path can:
- rewrite the shipped policy, the hook scripts or `vendor/`, which switches the guard off (a marketplace install is owned by the user, so this is the normal case);
- write into another version folder under the plugin's cache folder, or into Claude Code's `installed_plugins.json`: neither is a guard path, so code planted there runs in your terminal the next time you start the dashboard (the dashboard runs only a folder inside its own cache folder, and only when you start it);
- delete an added policy file (its rules go, with no message) or `state/*.calls` (which resets the step cap);
- edit or truncate the log;
- add a slow regex to an added policy file.

**The barrier meant for Bash writes (not tested here).** Claude Code's own Bash sandbox with unsandboxed commands switched off: `sandbox.enabled` set to true and `sandbox.allowUnsandboxedCommands` set to false, after which, per the Claude Code docs, Claude Code ignores the `dangerouslyDisableSandbox` parameter. Add `permissions.deny` rules for `Edit` on the plugin folder and the data folder (the docs write an absolute path as `Edit(//path/to/folder/**)`), and `sandbox.filesystem.denyWrite` for the same folders. The setting names were read from the current Claude Code docs on 2026-11-04; neither the sandbox nor these rules were run against this plugin. The sandbox limits writes to the working folder, so it does not cover a plugin folder inside the project; keep the plugin folder outside the project (install it from the marketplace, or copy it elsewhere). In interactive bypass mode an ask still stopped a call in one test on Claude Code 2.1.319 (limit 5), and a Claude Code upgrade can change that, so `ask-guard-paths` and `ask-claude-settings` may be weak there.

**Other limits.**
- The hook runs whichever `python3` comes first on `PATH`. Files that Python loads at start-up (for example `.pth` files and `sitecustomize` in its `site-packages`) can change what the Pre script does, including an exit 0 with no output, which Claude Code should read as allow; this was not tested. If Claude Code is started from an activated virtualenv inside the project, those files are in the project. Running the hook as `python3 -I -S` is a possible later change, not built.
- A repository you open can ship Claude Code project settings; whether those can set `GUARDRAILS_POLICY`, `PATH` or `PYTHONPATH` for the hooks, or switch the plugin off, was not checked here. The `ask-claude-settings` check covers only the four settings files (and the two in `CLAUDE_CONFIG_DIR` when set), only for write tools, and only on the project folder the hook reports (or `CLAUDE_PROJECT_DIR`) and the home folder. Claude Code's trust prompt for a new folder is the only other barrier known (not tested); reading `.claude/settings*.json` in an untrusted repository before you accept it is a step for you to take (untested).
- The guard check (not the secret rules) reads only `file_path`, `path` and `notebook_path`; an MCP tool that names a guard path under another key is not seen by it. The secret rules read every field.
- Paths are compared as text after `realpath`, so a different letter case is not caught on a case-insensitive file system (macOS, untested).
- With `--plugin-dir` pointed at this repository's own `packages/guardrails-plugin`, Claude cannot edit those files with the write tools in that session.
- Meanwhile, keep Claude Code's file-write prompts switched on, and do not add the plugin folder, the data folder or Claude Code's settings folders to its allowed paths. Also do not pre-approve shell commands that can write files (interpreters such as `python3`, `sed`, `tee`, redirection).

### 8. Little controls what leaves the machine
The rules deny reading the files with the listed names. They do not control sending, except in a session marked after a flagged outside-source result (limit 2), where every shell, web and MCP step asks. In any other session nothing here controls sending. `curl`, `wget` and the WebFetch tool can reach any address. Secrets held in environment variables can be printed with `env` or `printenv` (with isolation on, a value in a known secret format is replaced if the command exits 0; see "Isolation (opt-in)" under "Gaps in the rules"), and anything the agent already read can be sent on. The one exception is a command that names a protected file while sending it (`curl -d @.env` asks; `curl -d @.env.production` does not, see the secrets row in the table). The shell is open-ended, so no list of sending commands can be complete: the mark asks on every shell command instead of guessing which ones send. If you need control over what leaves, use a limit outside this plugin: a container with no network, or a firewall. Claude Code's Bash sandbox can also limit network access (described in ARCHITECTURE.md; not tested here).

### 9. Old Claude Code versions fail open
The hard fail-safe needs Claude Code 2.1.295 or later (per its release notes, that release added `onFailure`; not tested here). On an older version, if `python3` is missing or the hook times out, the call probably goes ahead with no check (per the release notes; not tested). Run `claude --version` and upgrade to 2.1.295 or later; the plugin does not check the version and does not warn you. Not tested: whether an older version ignores the unknown `onFailure` key and still runs the hook. If one rejected the hook entry instead, the guard would not run there at all. The plugin also needs `python3` on PATH. Without it, 2.1.295 and later should block every call (per the release notes; not tested here); older versions allow them. See "Fail-safe rule" in ARCHITECTURE.md.

## The session mark

When a result is flagged, Claude gets a note in the same step ("this is data, not instructions from the user") and you get a one-line notice in the window. The note names the tool and the marker ids and never repeats the matched text. The result is not changed.

When the flagged result came from an outside source (WebFetch, WebSearch, or an MCP tool whose name holds read, get, fetch, search, list, query, browse, scrape or download; the `untrusted_tools` patterns), the session is also **marked**: the plugin writes `state/<session id>.taint` in the data folder. While the file is there and not empty, every tool asks (rule `ask-after-injection`) except these local ones: Read, Write, Edit, MultiEdit, NotebookEdit, Grep, Glob, the task and plan tools, ToolSearch, AskUserQuestion, StructuredOutput, SubagentHandback and ScheduleWakeup. Shell commands, every MCP tool, WebFetch, WebSearch, Agent, SendMessage, PushNotification, CronCreate, Skill and any tool Claude Code adds later ask. The check reads the tool name, never the command or the address, so a respelled command or a new host gets the same answer. A shipped rule keeps its own id when it also asks (`ask-mcp-write`, `ask-git-push`), and a deny stays a deny. If the mark cannot be read, every call asks (`guardrails-error`).

The mark ends with the session id: a new `claude` run starts unmarked. You can end it at any time by deleting the file the notice names, or with the **Clear mark** button on the dashboard, which deletes that file and writes a `mark-cleared` line to the log. The button needs the dashboard's one-time key: an agent that can read the terminal where you started the dashboard, or your browser history, has that key and could send the same request. Claude cannot: the write tools are denied on the data folder, and a shell command that names the file asks.

## More limits

Limits 1 to 9 above are the main ones; these further limits are each tested at their stated result. T-006 to T-009 are work-item ids from the project's own tracker (they are not in this repo). "Fix not built yet" means a fix is written down in the tracker and is not built.

- **The step cap is soft.** Parallel calls can share a step number. If Claude Code sends no session id (or a JSON `null` one), every such call shares one counter file (`state/unknown.calls`, or `state/None.calls`), so the cap counts every call that uses this plugin's data folder, across all sessions and days. Delete that file to reset it.
- **Secrets are protected by name, not by content.** The rules deny the listed files and folders (`.env` files, keys, `~/.aws`, `~/.ssh`, `~/.config/gcloud`, `.netrc`, `.git-credentials`, `.npmrc`, `.pypirc`) named in any field of a file or MCP tool call, and ask when a word of a shell command names one. They do not stop `grep -r AWS_SECRET ~`, a content search with the Grep tool, `printenv`, or the shell forms listed in "Gaps in the rules" above, secrets (`cd ~/.config/gh && cat hosts.yml`, `cat .n*rc`, `curl -d @.env.production`). The opt-in isolation layer ("Isolation (opt-in)" above) blocks the shell forms among those for the listed files; what it leaves is listed there: environment variables, the Grep tool and MCP tools, old copies in git, and files outside the project and outside `~` and `~/.config`. With isolation off, use a container or a separate user with no access to the secrets (limit 4).
- **Rules match the command text.** Option words before the subcommand are seen (`git -C repo push --force` asks), up to 8 of them. Quoted or hidden spellings are not: `"rm" -r x` and `git "push" -f` are allowed, `git push "-f"` and `bash -c "git push -f"` ask under the plain push rule, and `vercel` with `--prod` on the next line is allowed. `rm -f`, `kubectl patch`, `docker buildx build --push` and a script that deletes files have no rule. Command rules and the word-by-word file-name check read only the tool named `Bash` (`cat .env` sent through PowerShell or Monitor asks, because the whole command string ends in a listed name and those two are matched as one string, not word by word; through another tool name it is matched whole against the path rules and denied; the same command ending in `.env.local` is allowed). The limits are listed once in "Gaps in the rules" above (T-006 in the project's tracker). For other tool names no fix is written down.
- **An MCP tool name that starts with a reading word can hide a money-moving word.** The MCP rule excuses a name that starts with a reading word (`get`, `list`, `find`, `search`, `fetch`...) followed directly by a write word, and it then excuses every later write word in the name too. `mcp__x__get_payment_then_transfer` and `mcp__x__list_payments_and_charge` are allowed, although they move money. The rule does not ask on them.
- **Over-matching.** The `deny-prod-config` patterns `*/prod/*` and `*/production/*` match a path, absolute, `~` or relative, with a `prod` or `production` folder below the project folder, or outside the project (a file tool is denied, a shell command asks). A project that itself sits in or behind such a folder is not affected: its own files are matched below the project folder. A relative path that leaves the project and spells no `prod` folder (`../other/x`) is not caught, as before. For Bash, every word of the command is treated as a possible path, so `git commit -m "fix production/config"` asks (rule `deny-prod-config`). Other false positives are listed in "Known false positives" below (for example `echo .env >> .gitignore` asks; adding `.env` to `.gitignore` with the Edit or Write tool is allowed). The MCP write rule is a name pattern and may ask for harmless tools (`mcp__x__postal_lookup`, `mcp__x__payment_status` and `mcp__x__get_user_payments` ask; the server name does not count, so `mcp__my_sender__list` is allowed); `except` does not work on it (see "Change the rules" in [ARCHITECTURE.md](ARCHITECTURE.md#change-the-rules)), so narrow its `match` pattern.
- **You cannot loosen a shipped rule from your own policy file.** A user who copied the shipped file and changed a deny to an ask keeps getting the deny. A switch kept in a file the agent can write is a switch the agent can flip. Edit the shipped file by hand if you must (a plugin update undoes the edit).
- **Other agents get less than Claude Code.** Codex hooks, the shell wrapper and an MCP client without elicitation cannot ask, so every ask is a refusal there. Cursor's own file edits are not checked. The shell wrapper sees only `-c` commands, the MCP proxy only stdio servers, and an agent that can edit its own config can take either out. The Cursor and Codex adapters are built from those agents' hook docs and tested with payloads in those shapes, not against the live agents. See "Other agents" in [ARCHITECTURE](ARCHITECTURE.md#other-agents).
- **The inventory is a list, not a control.** It reads names, paths and permission bits; it guesses what an MCP server can do from its name; it does not see account-level connectors. A CRITICAL level says the three legs of the lethal trifecta are present, not that data left.
- **Long commands ask.** A Bash command over 20000 characters is not checked by the rules. It always gets **ask** (rule `oversize-command`), even if it holds a deny pattern.## Log from one live session

## Limits of the log

- A declined ask leaves only the `decision` line, not a result line.
- A logged input longer than 2000 characters (the default of `audit.max_input_chars`) is replaced by `{"truncated": "<first 2000 characters>"}`, so the log shows only the start of a long command.
- Allowed calls that never ran (for example, an error before they started) are not logged.
- With no `tool_use_id`, Post cannot tell calls apart, and a result line can show another call's decision (ARCHITECTURE.md, "Audit and state").
- A call that ran and failed is sent by Claude Code to a separate event, PostToolUseFailure. `hooks.json` registers the Post script for it too, so the call gets a result line with `status` `error` (the event's input has `error` and no `tool_response`).
- An allowed call gets no line when it starts. Its only record is the result line written after it finishes. If the Post script fails, an allowed call that ran leaves no trace.
- If the decision memo cannot be written after the rules ran, the log line of a deny or ask is still tried on its own; if the data folder cannot be written at all, no line exists. An allow whose memo cannot be written becomes an ask.
- An `ask` caused by an internal error (reason starts with `[guardrails-error]`) is logged like any other decision when the data folder can be written. When it cannot be written there is no line, and if you approve the call and the Post script still works (it reads the shipped policy and the data folder too, so it fails after a broken shipped policy or an unset data folder), the result line shows decision `unknown`. The `guardrails-policy-error` ask (an added policy file left out) is a real decision and is logged.
- The write tools are denied on the log files, but a Bash command can still edit or delete them (limit 7). Treat the log as a help for you, not as proof of what happened.
- While the dashboard runs (`make dashboard` or the start command under "Get started" in the [README](../README.md)), its server listens on 127.0.0.1 only, and the address it prints carries a key that is new at every start. The server refuses every request without that key, so other login accounts on the computer, and a page from another site, cannot fetch the log through it even though the file is mode 0600. Anyone who sees the address (a shared screen, shell history) can. The hooks open no port; the plugin folder carries the dashboard server, and it runs only when you start it.
- State files are not cleaned up. Each session has its own counter file, so an old file does not affect a new session; only the shared files for a missing or null session id (`unknown.calls`, `None.calls`; see ARCHITECTURE.md, "Audit and state") carry over. Pre reads the whole `.calls` file and Post the whole `.decisions` file on every call, so the work per call grows with the file (not measured; a hook that runs past its 10-second timeout is blocked, for Pre, or loses its result line, for Post). Delete old state files.
- Redaction uses nine patterns (private key, Anthropic key, OpenAI key, AWS access key, AWS secret key, GitHub token, bearer token, JWT, the password inside a database address). The AWS secret key is caught only after the label `aws_secret_access_key=` or `aws_secret_access_key:` (with white space only between); the quoted JSON form `"aws_secret_access_key": "..."` and a bare 40-character secret are not. A secret in another format is written as is. Do not rely on redaction as the only protection for the log. New files are created with mode 0600, which keeps other users out and not the agent; an existing file keeps the mode it has.

## Known false positives

- `*/prod/*` and `*/production/*` deny a path, absolute, `~` or relative, that contains those folder names below the project folder or outside the project (`prod/x.txt` is denied too). A path that sits inside the project folder (by text: `~` expanded, joined to the hook's working folder, cleaned, compared with a `/` boundary) is matched on the part below it, so a project at `~/prod/app` or `/srv/production/app` keeps its files. A path outside the project is matched whole, as written; a relative one that leaves the project and spells no such folder (`../other/x` into a sibling production folder) is not caught. Links: with isolation on, the path fields of file tools are also resolved, so a project file that links out to a production folder is denied. In both modes a link named `production` inside the project is denied, as a folder of that name is. With isolation off no link is followed, so a link out is allowed: for a project under a `prod` or `production` folder that is weaker than before this rule (the whole path was denied then); for any other project it is as before. A project rooted at a production config folder itself (`CLAUDE_PROJECT_DIR=~/infra/prod`) has its own files allowed by this rule. An old full copy of the shipped `policy.json` in the data folder brings back `deny-prod-config` without `project_relative`, matched on the whole path, so it denies a project under a `prod` folder again. For a shell command, every word counts as a possible path, so `git commit -m "fix production/config"` asks too.
- `deny-env-files` matches any word of a Bash command that looks like an env file name, even when the command only writes the name. `echo .env >> .gitignore` and `cp .env.example .env` both ask (the second because of the target `.env`). To add `.env` to `.gitignore`, use the Edit or Write tool: their text is not checked, so that is allowed.
- Every string of an MCP tool, or of any tool that is not a built-in one, is matched whole against the path rules, and a glob with a `/` matches anywhere in the string. An MCP message that contains `config/prod/db.yml` is denied (`deny-prod-config`), and so is one that contains `~/.aws/config` (`deny-credential-dirs`). A string that ends in `.env`, `.key` or `.pem` is denied too, so an MCP write of `.gitignore` text that ends in `.env` is denied. Prose that has `.env` in the middle passes. How often MCP text holds such paths was not measured. The deny names its rule; do the step with a built-in tool.
- `cat .npmrc` and `cat .pypirc` ask in every folder, also when the file holds only a registry address, because the rules cannot tell the two apart by name. `ls ~/.aws` and `cat ~/.aws/config` ask, because the folder is listed whole.
- The MCP rule matches a write word at the start of any word of the tool name, so harmless tools ask: `mcp__x__postal_lookup`, `mcp__x__payment_status`, `mcp__x__transfer_status` and `mcp__x__get_user_payments`. `mcp__blog__get_post` and `mcp__my_sender__list` are allowed.
- The command rules read the whole command text, including quoted text: `git commit -m "never git push --force"` asks under `deny-force-push`.
- The production rule also covers `*.prod.yaml`, `*.prod.yml`, `*.prod.json` and `*.prod.tfvars`, so a file such as `app.prod.json` is denied.
- The recursive-delete ask has no command boundary: `git rm -r x` asks, and so does `rm a; ls -R` (the pattern runs past the `;` to a later `-R`).
- `.env*` also denies `.envrc` and `.environment`. `*.key` denies any file that ends in `.key`. `cat ~/.ssh/id_rsa.pub` asks under `*/.ssh/*`, although the key-file rule excepts `*.pub`.
- `ask-git-push` asks for every push written as `git push`, including safe ones. That is on purpose.

## Design stance: a denylist, not least privilege

The design assumes the agent is useful but fallible. Deny the listed things that are rarely right where the guard can hold every spelling: a path field of a file or MCP tool (the false positives above show the rules are not exact). For shell commands, ask: shell text can be spelled another way, so a deny there would claim a refusal the guard cannot keep. The barriers for the shell are the sandbox (isolation) and server-side settings such as a GitHub ruleset. Ask for the listed things that are sometimes right and hard to undo. Allow the rest, including every command with no rule. This is a denylist: it approximates least privilege and does not reach it (see the [GLOSSARY](../GLOSSARY.md), "least privilege" and "blast radius"). A mistake is stopped or shown to a person only when it is written in a listed spelling, on a listed target, and (for an ask) when someone can answer; anywhere else it is not covered.

## Alternatives considered

Other designs were weighed in [ARCHITECTURE.md](ARCHITECTURE.md) ("Alternatives at a glance"). One is deferred, not rejected: a built-in minimum deny list (no work item); the reason is priority only. Counting the step after the rules is built (T-007). Not weighed as alternatives: isolation instead of this plugin (isolation is the control for limits 2 to 4 and 8, and this plugin adds an ask with a reason and a log on top of it; T-014 added an opt-in isolation layer for shell reads of secret files, and its rejected designs are in ARCHITECTURE, "Alternatives at a glance"), and showing the injection warning to the user (now built: the person sees a notice and Claude gets a note).

Set aside, with reasons:

- An allowlist instead of a denylist: it blocks every command not listed, so each command the agent needs must be added first ("Other choices" in ARCHITECTURE.md).
- Deny instead of ask on an internal error: a deny on every error would stop all work, and an ask lets a person continue ("Fail-safe rule"). A deny from a rule is no longer turned into an ask by an internal error.
- Match more Bash write spellings (`$HOME`, environment-variable names, redirects, `sed -i`, interpreters): the set of spellings is open-ended, so the work would never end. The sandbox is the intended barrier (limit 7).
- Block or rewrite instead of scan, tell and mark for injection: a phrase match has false positives (the markers match ordinary local files and security write-ups), and rewriting makes the model see text that differs from the tool's real output ("Cuts").
- Claude Code's own `permissions.deny` and sandbox instead of this plugin: they need no Python and do not depend on a hook timeout, but they show no per-rule reason and are not known to keep an audit log (not checked); the two can be used together ("How this relates to Claude Code's own controls").
