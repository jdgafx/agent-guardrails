# Architecture

agent-guardrails is a Claude Code plugin. Claude Code runs a small script (a hook) before and after each tool call; this plugin's scripts check the call against rules in `policy.json`. The first script (Pre) answers deny, ask or allow and logs each deny and ask (a decision line, with exceptions: see "Fail-safe rule"); the second (Post) logs each call that ran (a result line, when the Post script works). This document explains how it is built and why. What it does not protect is in [THREAT_MODEL.md](THREAT_MODEL.md); install steps are in the [README](../README.md); unfamiliar words are in the [GLOSSARY](../GLOSSARY.md).

Short forms used below: **Pre** and **Post** are the two scripts, `hooks/pre_tool_use.py` (runs before the call) and `hooks/post_tool_use.py` (after it). The **data folder** is the folder Claude Code gives the plugin through `${CLAUDE_PLUGIN_DATA}`; it is outside the plugin folder and survives plugin updates (as Claude Code documents it; not tested here), and it holds `audit/`, `state/` and an optional `policy.json` of your own. **Bypass mode** is Claude Code run with permission checks off.

## Problem and goals

- **Problem.** An agent that runs commands and edits files can do something destructive or expose a secret by mistake, and Claude Code is not known to keep a per-call record of what a guard allowed, asked or denied (not checked).
- **Goals.** Deny the commands and file names that `policy.json` lists, in the listed spellings. Ask a person before the commands `policy.json` lists as ask. Keep a redacted log.
- **Non-goals.** A spend cap, injection blocking, an exporter, a UI (see "Cuts"), and protection against a determined attacker (see [THREAT_MODEL.md](THREAT_MODEL.md)).

## Modules (in guardrails-core)

| File | Job |
|------|-----|
| `hooks.py` | The two entry points, `run_pre` and `run_post`, and the `ask` that Pre returns on an internal error. Pre runs the guard check and the rules before anything that can fail (the policy of the user, the data folder). With isolation on, Pre also runs the tripwire and Post also redacts shell output. |
| `rules.py` | Turns (tool name, tool input, step) into deny, ask or allow (`match`, `cap`, `evaluate`), and holds the guard check (`guard_paths`, `guard_check`, `stronger`). `match` takes an optional `cwd`: with it, a path field of a non-Bash tool is also matched in its resolved form (the link check of isolation). The shell-ask rule is its last step: a deny of kind `path` or `command` on a shell tool (`SHELL_TOOLS`: Bash, PowerShell, Monitor) is returned as an ask with the same rule id. |
| `policy.py` | Loads the shipped `policy.json`, checks every policy file against `policy.schema.json` in full, and merges the added policy files into the shipped one. |
| `audit.py` | Writes log lines, counts calls, remembers Pre's decision for Post. |
| `injection.py` | Scans the output of every tool that is not trusted (`trusted_tools`) for injection phrases and logs a warning; a record, not a shield. It reads the text values of the result (not keys, numbers or base64 data), applies NFKC, removes invisible format characters, collapses white space and keeps the first 200000 characters. Markers match without regard to case. One 3-second timer covers the whole scan (not on Windows or off the main thread). |
| `redact.py` | Replaces known secret formats (seven patterns; the names are in the README) with `[REDACTED:kind]`. `redact_fields` does it for chosen keys of a dict (used for shell output with isolation on). |
| `isolation.py` | The opt-in isolation layer: `sandbox_block` generates the Claude Code sandbox settings block from the secret rules, `block_in_force` checks that a project's settings files hold it and open no sandbox write path or host, and `python3 -m guardrails_core.isolation <policy.json>` prints the block (`make isolation`). |

## What happens on one tool call

Claude Code runs one hook before a tool call (the `PreToolUse` event) and one after the call finishes (the `PostToolUse` event).

```text
Claude wants to run a tool
        │
        ▼
PreToolUse hook  (hooks/pre_tool_use.py → guardrails_core.hooks.run_pre)
  1. read JSON from stdin and check it
  2. guard check: a write tool (or any MCP tool) on a guard path is deny, rule "deny-guard-files"; a write tool on one of the four Claude Code settings files (or the two in `CLAUDE_CONFIG_DIR`) is ask, rule "ask-claude-settings"; a Bash command with a word that is an absolute or ~ path inside a guard path is ask, rule "ask-guard-paths"
  3. load policy: the shipped policy.json in the plugin folder, then the file named by the GUARDRAILS_POLICY environment variable, then <data folder>/policy.json, each added file checked against the schema and merged in (it can only add; `trusted_tools` is the one key that turns something off, a log warning); an added file that fails is left out and its error kept; a shipped policy that fails ends the call with ask (a guard deny from step 2 stands)
  4. if a Bash command is over 20000 characters: ask, rule "oversize-command", and skip the rules
  5. check every rule, whatever its kind (path, command or tool name); strongest wins (deny beats ask; the guard result of step 2 wins a tie). A deny of a path or command rule on Bash, PowerShell or Monitor is returned as ask, with the same rule id and a note in the reason (the shell-ask rule); a tool rule and every other tool name keep the deny. With isolation on (`"isolation": true` in an added policy file), step 5 adds two checks: the link check (a path field of a non-Bash tool is also matched as resolved, so `Read` on a link to `.env` is denied) and, for Bash, PowerShell and Monitor, the tripwire (deny, rule "isolation-not-active", when the sandbox block is not in force in the project's `.claude/settings*.json`; see "Isolation (opt-in)")
  6. if no rule matched and an added policy file was left out: ask, rule "guardrails-policy-error", with the file and the error
  7. count the step (state/<session>.calls); an allow that cannot be counted becomes ask, a deny or ask stands
  8. if no rule matched and step > cap: ask, rule "step-cap"
  9. remember decision, rule and step (state/<session>.decisions)
 10. deny/ask: write a "decision" audit line, print the JSON answer
     allow: print nothing
        │
        ▼  (Claude Code acts on the answer; see the note below)
        │
PostToolUse hook (hooks/post_tool_use.py → run_post)
  1. read JSON from stdin and load the policy (as Pre does, with the added policy files; a failure of the shipped policy ends the call with an error and no log line)
  2. with isolation on and the tool Bash, PowerShell or Monitor: replace known secret formats in the `stdout` and `stderr` strings of the response (`redact_fields`)
  3. in one try: check the data folder is set (an unset one means no log line), look up what Pre decided for this tool_use_id, unless the tool is trusted (`trusted_tools`; `untrusted_tools` wins over it) scan the output (for a failed call, its error text) for injection phrases, and write a "result" audit line (redacted, with any warnings; it uses the original response)
  4. print nothing, and the conversation is never changed, except in one case: when step 2 changed the output, print one JSON object (`updatedToolOutput`, plus a `systemMessage` if step 3 failed) and exit 0. Without that change, a step 3 error is raised and the script exits 1.
```

Between the two hooks, Claude Code enforces deny, asks you on ask, and on allow carries on with its own normal permission prompts. This is Claude Code's documented behaviour and is not tested here; for bypass mode see limit 5 in [THREAT_MODEL.md](THREAT_MODEL.md).

### Hook input and output

Both hooks read one JSON object from standard input. It must have a non-empty text `tool_name`. If `tool_input` is present it must be an object. Pre also reads `cwd` (the folder Claude Code runs in, which it sends with every hook call per its hook docs; not tested here) to resolve relative paths in the guard check; if it is missing or not text, the hook's own working folder is used. `session_id` is optional (a missing one becomes `"unknown"`; an empty one also counts in `unknown.calls`, but the log keeps it empty), `tool_use_id` is optional (a missing one means no id), and Post also reads `hook_event_name` and `tool_response` (a PostToolUseFailure input has no `tool_response`; Post then scans and measures its `error` text). Pre prints nothing for allow. For deny and ask it prints one JSON object: `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny" or "ask", "permissionDecisionReason": "[rule-id] reason text"}}`, and it exits 0 on every path the wrapper covers (a failed import is covered; a crash outside the wrapper is not). A `session_id` that is JSON `null` is not replaced by the default: the call counts in a file named `None.calls`. Post prints nothing; it exits 0 when its log line was written and 1 when it was not (Claude Code documents 1 as a non-blocking error; not tested here). The one exception is isolation: when Post changed shell output it prints `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "updatedToolOutput": <the response with stdout and stderr redacted>}}` (with a top-level `systemMessage` "guardrails audit failed: ..." if the log write failed) and exits 0.

## Fail-safe rule

Each failure has one owner. Layer 1 is the hook script itself. Layer 2 is Claude Code, for failures where the script cannot run at all.

### Layer 1, inside the script (answer: ask)

`PreToolUse`: the rules run before anything that can fail, so a deny stays a deny. The step numbers here are those of the diagram above. If Python runs but the import of the vendored core fails (a missing `vendor/` folder), the wrapper in `pre_tool_use.py` catches that and asks. Inside the engine:
- An exception in step 1 (bad input) gives `ask` with a `guardrails-error` reason and exit code 0, and a log line when the data folder can be written (tool name `unknown` and an empty input when the input could not be read).
- The guard check (step 2) needs no file in the data folder, so it runs first. If the shipped policy then cannot be loaded (step 3), a guard deny (a write tool on a guard path) still stands and is logged when the data folder can be written; any other call gets `ask` with a `guardrails-error` reason, even `cat .env`. This is the one case where a would-be deny is an ask, and the price of not having a built-in minimum deny list.
- An added policy file that cannot be read or fails the schema does not stop the rules: it is left out, the shipped rules run, and a call that no rule matched gets `ask` with rule `guardrails-policy-error` naming the file and the error. That ask is a real decision: it is counted, saved in the memo and logged.
- An unset data folder, a data folder that is a file, or a read-only `state/` stops only the counting and the logging (steps 7, 9 and 10). A deny or ask from the rules stands. A call that no rule matched is an allow that cannot be counted, so it becomes an ask with a `guardrails-error` reason.
- An exception in step 9 or 10 (save the decision memo `state/<session>.decisions`; write the log line, deny and ask only) comes after the rules ran: a deny stays a deny, an ask stays an ask, and an allow becomes an ask, because an allowed call whose memo failed would otherwise go unrecorded. (If nothing could be written, Post's own result line, when it succeeds, shows decision `unknown`.) The memo and the log line are tried separately, so a failed memo no longer loses the log line of a deny or ask.
An `ask` caused by an internal error (a `guardrails-error` reason) is logged like any other decision: Pre writes a decision line and a memo with rule `guardrails-error` when the data folder can be written (the helper the guard-deny fallback uses; for input it could not read, the line has tool name `unknown` and an empty input, and the raw text is not logged). The ask does not depend on the write: when nothing can be written, and the user approves the call and the Post script works (it reads the shipped policy and the data folder too), Post finds no memo and writes decision `unknown`, rule and step null.

### Layer 2, in Claude Code (answer: block)

Layer 1 cannot run if Python never starts or the hook is killed. By default, Claude Code lets the call go ahead when a PreToolUse hook can't start, times out, or exits with an unexpected code (not 0 or 2). Exit 0 means success; exit 2 is the code a hook uses to block a call. So `hooks.json` sets `"onFailure": "block"` on the PreToolUse hook (Claude Code 2.1.295 or later). Then a missing `python3`, a crash outside the wrapper, or a timeout should block the call. On an older Claude Code those cases probably fail open, but this was not tested: an older version might instead reject the hook entry, and then the guard would not run at all (limit 9 in [THREAT_MODEL.md](THREAT_MODEL.md)). Source: the Claude Code 2.1.295 release note, "Added `onFailure: "block"` for command and HTTP hooks: a hook that can't start, times out, or exits with an unexpected code blocks the action instead of letting it through." No link to the note was recorded. The block itself and the timeout are not tested here, and this whole layer rests on that note.

|---------|----------------|--------|--------|
| Broken JSON or no tool name | Pre script (layer 1) | ask | yes |
| Added policy file missing, unreadable or invalid | Pre script | the file is left out; deny and ask rules still decide; a call no rule matches asks with rule `guardrails-policy-error`. In bypass mode an ask may not stop the call (limit 5) | yes. `cat .env` stays an ask under its rule, `git push` an ask, `ls` the policy-error ask (`test_broken_added_policy_keeps_denies_and_asks_on_unmatched_calls`) |
| Data folder unset, a file, or `state/` read-only | Pre script | a deny stays a deny; a call no rule matched asks (`guardrails-error`) | yes (`tests/unit/test_t007_self_protect.py`, cases 23 to 27) |

| `python3` missing, a crash outside the wrapper, or a timeout | Claude Code, through `"onFailure": "block"` on the PreToolUse hook (2.1.295 or later) | should block (per the 2.1.295 release note). On older versions the call probably goes ahead (untested; the guard might not run at all) | exit code only (`test_no_python3_exits_non_zero_so_onfailure_block_applies`); the blocking and the timeout are not tested |

Post has no `onFailure`. Claude Code documents exit 1 as a non-blocking error (not tested). With isolation on and a secret redacted from shell output, a failed log write does not lose the redaction: the redacted output is printed with the error as `systemMessage`, exit 0 | the isolation case yes (`test_case_48_post_with_an_unwritable_log`); the plain error no |

### Slow input

Regex time grows with input size, and a timed-out hook is a failure of layer 2. Post also runs user-supplied regexes (the injection markers, on up to 200000 characters) under the same 10-second timeout with no `onFailure`: a Post timeout loses that call's result line and blocks nothing. The scan guards against that. The shipped markers use only bounded repeats (`\s{1,3}`, `{0,60}`), white space is collapsed to one space before they run, and the whole scan runs under a 3-second timer (`signal.setitimer`; Linux and macOS, main thread): when it fires, the warnings found so far stay, the line gets a `scan-timeout` warning that names the marker, and the line is still written. Without a timer (Windows, or off the main thread) a slow marker, shipped or added, can still run into the 10-second timeout; the shipped markers are tested at under 1 s each on 21 repeated inputs of 200000 characters (`test_case_35_every_marker_is_fast_on_every_seed`). Two measures, with different jobs. The size cap carries the load: the rules never see a Bash command over 20000 characters; it gets `ask` with rule `oversize-command`, so a deny pattern inside a huge command becomes an ask. The shipped regexes were also rewritten to avoid the slow case, as a second line. With the cap switched off in a test (`test_regexes_scan_in_linear_time` sets the constant `MAX_COMMAND_CHARS` in `rules.py` very high), the test runs three repetitive inputs of 60 to 180 KB (`rm `, `git push `, `vercel `, each repeated 20000 times and followed by `; cat .env`) and asserts that each finishes in under 5 s with the answer still deny. A hand measurement of the `rm rm rm ...` case gave 0.2 s (it took 23 s before the regexes were rewritten; the test comment records this). Python's `re` can backtrack, so this is a measurement on these shapes, not a proof. Redaction runs on the whole tool input before the log cut, and the cap does not cover it; timed by hand on one Linux machine it took 0.2 s on 5 MB of plain text and 0.1 s on 3 MB after `Bearer ` (no test). The 20000 limit is that constant in `rules.py` and cannot be set in `policy.json`. The 200-call step cap is `step_cap.max_calls` in the shipped `policy.json`. The 10-second hook timeout is set in `hooks.json`.

### Why ask, and what is not built

Why ask and not deny on an internal error? A broken guard should not stop all work: an ask lets a person continue, while a deny on every error would stop every call. (It keeps a human in the loop only when someone can answer: not in `claude -p`, limit 6, and not in bypass mode, limit 5.) Layer 2 cannot show a prompt: the setting the release note describes is `onFailure: "block"`, not an ask. So a missing `python3` should stop every call until the user fixes it (on 2.1.295 or later; see layer 2).

Counting the step after the rules is built (T-007): the rules run first, so a full disk or an unwritable data folder no longer turns a deny into an ask. One alternative is not built. It is deferred, not rejected: no technical blocker is known and no reason beyond priority is recorded. A built-in minimum deny list would apply when the shipped policy cannot load; it is not built, has no work item, and would be a second set of rules that must agree with `policy.json`. The price today is that a missing or broken shipped policy turns every call, except a guard deny, into an ask.

## Decision: vendoring, not a pip install

The hook runs as `python3 hooks/pre_tool_use.py` on whatever `python3` the user has. A plugin install is expected to be a plain folder copy. Not checked: whether `/plugin install` runs any package-manager step.

So the plugin cannot depend on a package from the workspace. Options considered:

| Option | Why not |
|--------|---------|
| `pip install guardrails-core` at install time | A plugin install is expected to copy the folder with no package-manager step (not confirmed; see above). It would also need network access, which the README says the plugin does not use ("No network. No pip install."). |
| A venv inside the plugin | Not portable between machines: a venv holds absolute paths and compiled files for one machine. |
| A `SessionStart` hook that builds the code in the data folder | Not built: it adds a start-up step that can fail before the guard exists, and the committed copy needs none. |
| One big file written by hand | Hard to test and review as one unit. |
| One big file generated from core and drift-checked like `vendor/` | Would work. Not chosen: it is the same copy-and-check idea with a harder file to read in a diff. |
| A symlink or a git submodule to core | Not used: a link that points outside the plugin folder may not survive an install that copies the folder (not checked), and the committed copy needs no such assumption. |
| Put all the code inside the plugin folder (no separate core package, no copy) | Would work with no copy and no drift check. This is a scope decision, not a technical one: the brief for this project (not in this repo) asks for a core package, a plugin and a demo (the acceptance test `tests/acceptance/test_t001_done.py` checks that those folders exist). The price is the two gaps below. |
| **Vendor core into the plugin** | Chosen. `make build` deletes `packages/guardrails-plugin/vendor/guardrails_core/` and copies `guardrails-core/src/guardrails_core/*.py` into it (a hand edit in `vendor/` is lost; a file deleted from core disappears from `vendor/` too). The hook adds `vendor/` to `sys.path`. |

The vendored copy is **committed**, so `claude --plugin-dir` works from a fresh clone with no build step. Two checks look for a stale copy, and each has a gap:
- A unit test compares every vendored file byte for byte with core. `make test` runs `make build` first, which refreshes the copy, so under `make test` this test cannot fail. It can fail only when you run `pytest` directly.
- CI runs `make build` and then fails if `git status --porcelain` lists anything under the vendor folder, new untracked files included (before T-009 it ran `git diff`, which ignores files git does not track yet), so a new core module whose vendored copy was never added to git fails CI instead of reaching a fresh clone. There its import would fail and every call would get `ask`. A local `make test` runs `make build` first, so it cannot see drift; CI runs the check before `make test`. After `make build`, run `git status` and add new files.

Cost: two copies of the same code in git, and the CI gap above. Gain: the plugin needs only `python3` on PATH and no install step.

## How this relates to Claude Code's own controls

Claude Code has two built-in controls that overlap with this plugin. The first is permission rules in its settings (`permissions.deny` and `ask`). They run inside Claude Code, need no Python and do not depend on a hook timeout. The second is a Bash sandbox that limits, at operating-system level, what shell commands can read, write and reach on the network. The sandbox can limit what a script reads, depending on its settings; this plugin only sees `python script.py`, not what is inside. The plugin's opt-in isolation layer uses the sandbox's read masks for the secret list (tested live; see "Isolation (opt-in)" below); the sandbox's defaults and its use as a write barrier were not tested. It is also the barrier meant for Bash writes to this plugin's own files (limit 7 in [THREAT_MODEL.md](THREAT_MODEL.md)): `sandbox.enabled` true, `sandbox.allowUnsandboxedCommands` false (Claude Code then ignores `dangerouslyDisableSandbox`), `sandbox.filesystem.denyWrite` on the plugin folder and the data folder, and `permissions.deny` rules such as `Edit(//path/to/folder/**)`. The setting names were read from the current Claude Code docs on 2026-11-04; the write settings (`denyWrite`, `permissions.deny` on the guard's folders) were not run against the plugin. The sandbox writes only to the working folder by default, so it does not cover a plugin folder inside the project.

This plugin does not replace them. What it adds, over `permissions.deny` and `permissions.ask`, is a reason shown with each ask or deny, one policy file that installs as a plugin, and an audit log. The two can work together. A Claude Code release note reportedly states that a `permissions.deny` rule wins over a hook that answers `ask`. The version and the exact text were not recorded here and are unverified. Check the release notes yourself; if it holds, put the few things that must never run in `permissions.deny` and use this plugin for the ask tier and the log. This plugin does not depend on that change. Whether a plugin can ship permission settings itself has not been checked, so a user who wants `permissions.deny` must add it by hand.

## Other choices

In one line each:
- Denylist, not allowlist: an allowlist blocks every command that is not listed, so each command the agent needs must be added first. The cost is that every command not on a list runs (see the limits in THREAT_MODEL.md).
- Ask, not deny, on an internal error: explained under "Fail-safe rule".
- Added policy files merge into the shipped one and can only add (`trusted_tools` turns off only the injection scan, a log warning), instead of one file replacing the other: a replacement can loosen a rule, so the agent (or a typo) could switch the shipped rules off. The cost is that a user cannot loosen a shipped rule from their own file; an `extends` field that let an added rule replace a shipped one was rejected for the same reason.

## Policy

- `policy.json` has `version` (must be `1`), `isolation` (true or false, default false; the opt-in isolation layer), `rules`, `step_cap`, `untrusted_tools`, `trusted_tools`, `injection_markers` and `audit` (the log settings `max_input_chars` and `otel_field_names`).
- Only `version` is required at the top level, so an added file can hold just `{"version": 1, "isolation": true}`. The shipped policy must also have `rules` and `step_cap.max_calls`. When `rules` is present it must not be empty, and rule ids must be unique. A rule has an `id`, a `decision` (`deny` or `ask`; `allow` is not a rule decision), a `kind`, `match` patterns (a non-empty list of text) and a `reason` (all required), and an optional `except` list that only `path` rules read:
  - `path`: glob patterns on every string of the tool input, at any depth and inside lists, dict keys included, except the text fields in `TEXT_FIELDS` in `rules.py` (the text that built-in tools write, search for or send: Write `content`, Edit `old_string` and `new_string`, Grep `pattern`, WebFetch `url` and `prompt`, SendMessage `message`, TaskCreate `description`, and so on; the table lists the built-in tools seen on 2026-11-05, and a tool or prose field missing from it is checked in full, so it can cause a visible deny, never a silent allow). Each string is matched whole. For a Bash command, also on every word of the command, not only words that look like paths; words are split on any white space (spaces, tabs, line breaks) and on `; & | < > = ( ) " '` and the backtick. A glob without a `/` matches the file name only. A glob with a `/` matches the whole path (with a `/` put in front, so `*/.ssh/*` also matches `.ssh/id_rsa`), or on a rule with `project_relative` the part below the project folder (see "Change the rules" in the README; `rules.path_hit` picks the form, `rules._below` computes it by text, with no disk call). Matching ignores upper and lower case. Each string is tried as written, with a leading `~` expanded, and with `/./`, `//` and a trailing `/` removed (`os.path.normpath`). `except` globs excuse a match. The guard check reads only the named path fields (`file_path`, `path`, `notebook_path`).
  - `command`: regular expressions on the Bash command, found with `re.search`, so they are not anchored. Case-sensitive. Applies only when the tool is named exactly `Bash`; a command run through any other tool gets no command rule, and its string is matched whole against the path rules (`cat .env` through PowerShell or Monitor asks, through another tool name it is denied, and a string that ends in `.env.local` is allowed; see limit 4 in [THREAT_MODEL.md](THREAT_MODEL.md)). `except` is ignored here, with no message.
  - `tool`: regular expressions on the tool name. Case does not matter. `except` is ignored here too.
- If several rules match, deny beats ask. Among rules of the same strength, the first one in the file is the one reported.
- `untrusted_tools` patterns are regular expressions on the tool name and are case-sensitive (the shipped MCP pattern starts with `(?i)`, so MCP names match in any case). `trusted_tools` patterns work the same way. Post scans a call unless a `trusted_tools` pattern matches the tool name and no `untrusted_tools` pattern does. The shipped policy has no `trusted_tools`, so every tool is scanned, tools that do not exist yet too. An added file may set `trusted_tools`: it is the one key that turns something off, and what it turns off is a log warning, never a deny or an ask.
- `policy.schema.json` is the JSON Schema, and it is enforced. `validate(p, schema)` walks the whole of `policy.schema.json` with a small checker (about 30 lines, no `jsonschema` package, because the plugin runs on the stock `python3` with no install step). It knows the keywords the schema uses (`type`, `required`, `properties`, `additionalProperties: false`, `items`, `enum`, `const`, `minItems`, `minLength`, `minimum`), skips the annotations `$schema`, `title` and `description`, and refuses any other keyword, so a later schema edit cannot add a check that does nothing. A JSON `true` is never an integer, and `const` and `enum` compare the type as well as the value (`true` and `1.0` do not equal `1`). After the walk it checks that rule ids are unique within a file and that every regex compiles. So a text `except`, an unknown key such as `step-cap`, a missing `max_calls`, a `max_input_chars` under 100 and a text `untrusted_tools` are all errors. Two things stay outside the schema: that `except` is on a `path` rule (on a `command` or `tool` rule it passes and does nothing; the schema allows it), and that the shipped policy has `rules` and `step_cap.max_calls` (the shipped policy must have them; the schema does not require them).
- Merge: the added rules are appended after the shipped rules (an added rule equal to a shipped one is skipped); `step_cap.max_calls` is the smaller of the shipped and added values; `untrusted_tools`, `trusted_tools` and `injection_markers` are the union; `isolation` is true once any file says true (an added file cannot turn it off); `audit` in an added file is ignored. The shipped rules come first and the rule loop stops at the first deny, so a slow regex in an added file cannot delay a shipped deny on a file tool or a tool rule. A shell text rule only asks and an ask does not stop the loop, so a slow regex in an added file can delay a shipped shell ask.
- `validate()` checks that a pattern compiles, not that it is fast. A pattern you add can be slow enough to hit the 10-second hook timeout. On Claude Code 2.1.295 or later the call should then be blocked (layer 2, untested); on older versions it probably runs unchecked (untested).

## Trust boundary

The guard trusts the files it is made of, and protects some of them. Protected against the write tools (Write, Edit, MultiEdit, NotebookEdit and any MCP tool, rule `deny-guard-files`): the plugin folder (the shipped policy, the hook scripts, `vendor/`, `hooks/hooks.json`), the data folder (`state/*.calls`, `state/*.decisions`, `audit/*.jsonl`, an added `policy.json`) and the file named by `GUARDRAILS_POLICY`. The guard paths are known only at run time, so the check is code in `rules.py`, not a pattern in `policy.json`. Each path goes through `~` expansion, is joined to the hook input's `cwd`, and goes through `os.path.realpath`; a path is inside a guard path when it equals a guard file or equals or starts with a guard folder plus `/` (so `<data>2/x` is not inside `<data>`). A link in the project that points into the data folder is caught. Not protected: anything a Bash command writes without naming a guard path as an absolute or `~` path (limit 7 in THREAT_MODEL.md), Claude Code's own settings files beyond an ask (`ask-claude-settings`, four files), and the Python start-up files of the `python3` the hook runs.

Policy loading, in order; the shipped policy always loads first and added files can only add (`trusted_tools` aside):
1. The `policy.json` in the plugin folder. It must load, pass the schema and have `step_cap.max_calls`, or the call asks.
2. The file named by the `GUARDRAILS_POLICY` environment variable, if the variable is set and not empty. If that path does not exist or is a folder, it is an error: the file is left out and the ask names it.
3. `${CLAUDE_PLUGIN_DATA}/policy.json`, if the data folder is set and anything exists at that path (a link counts as existing). It survives plugin updates. Anything there that is not a regular file (a folder, a dangling link, a pipe) is an error. A path that does not exist is not an error: that is the normal case.

An added policy file can only add to the shipped one (`trusted_tools` aside). A missing or broken added policy file is left out, the shipped rules still apply, and calls no rule matches ask, with the file and the error in the reason. Deleting an added file removes its rules with no message. After updating the plugin, check your policy file against the schema; you no longer need a full copy of the shipped file.

## Isolation (opt-in)

Goal: close the shell forms that no rule can match (a built name, a glob, a parent folder, a link made before the call) for the listed secret files, by isolation and not by more matching. The plugin builds no sandbox of its own. It generates a settings block for Claude Code's Bash sandbox and adds two checks and one redaction. It is off by default (`"isolation": false`); the README has the user-facing table and the costs.

- **The block** (`isolation.sandbox_block`). Input: the `match` and `except` globs of the first rule with each id in `ISOLATED_RULES` (`deny-env-files`, `deny-credential-dirs`) in the shipped policy; added rules never change it (`test_case_35_added_policy_files_do_not_change_the_block`). Each glob loses a leading `*/` and a trailing `/*` and is written under three anchors: `./**/` (anywhere in the project), `~/` and `~/.config/`. Output: `sandbox.filesystem.denyRead` (39 entries) and `allowRead` (the `except` globs, 9 entries), and `enabled`, `failIfUnavailable` and `allowUnsandboxedCommands: false`, and `autoAllowBashIfSandboxed: false` (so Claude Code's own prompts and allow rules work as before). It never writes an entry that starts with `~/**` or `/**`: on a 4.5-million-file home folder each sandboxed command took 100 to 187 seconds with `~/**/` entries. The committed `isolation/settings.local.json` must equal the generator's output (`test_case_34_block_comes_from_the_secret_list_and_matches_the_committed_file`); `make isolation` rewrites it.
- **Where the block goes.** In the project's `.claude/settings.local.json` (or `.claude/settings.json`): only in project and local settings does `./` mean the project root. A plugin cannot ship sandbox settings (its `settings.json` keeps only `agent` and `subagentStatusLine`), so the user copies the file.
- **The tripwire** (`isolation.block_in_force`, called from `hooks.run_pre`). For Bash, PowerShell and Monitor calls with isolation on, Pre reads `.claude/settings.json` and `.claude/settings.local.json` of `CLAUDE_PROJECT_DIR` (or the hook's `cwd`), merges them as Claude Code does (a boolean from the local file wins, lists are joined) and denies the call, rule `isolation-not-active`, unless: the four flags have the block's values, every generated `denyRead` entry is present, `allowRead` holds nothing else, and the `sandbox` object holds no key outside a closed list (the block's own keys, `filesystem.denyWrite` and `network.deniedDomains`, which only narrow). A closed list, not a list of weakening keys, so a setting that a later Claude Code adds cannot slip past. `filesystem.allowWrite` and `network.allowedDomains` are outside the list: a project file could ship either one. Outside `sandbox` no closed list is possible, so the check covers exactly the project settings that the Claude Code docs name as sandbox write or host sources (`_grants`): any `permissions.additionalDirectories`, any `Edit` entry in `permissions.allow`, and any `WebFetch(domain:...)` entry in `permissions.allow`, which the docs add to the same host list as `allowedDomains` (the text before the first `(` is the tool name, so no path or host is matched; a bare `WebFetch` rule adds no host and passes). A new source in the docs is a new row there. Extra write folders and trusted hosts belong in the user's own settings, which Pre cannot see. An unreadable file, invalid JSON or an exception is a deny, never an ask: an unchecked shell call is what the layer exists to stop. An empty file counts as no file, because the sandbox leaves a zero-byte placeholder for `.claude/settings.json` while a command runs and a parallel call's Pre can see it (seen in the live run on 2026-11-06). It is a check for user mistakes, not a barrier: the hook input carries no sandbox state, and Pre cannot see managed settings, a `--settings` flag, `--setting-sources`, `--add-dir` or a user settings file.
- **The link check** (`rules.match` with `cwd`). With isolation on, the resolved form of each path field of a non-Bash tool is also matched against the path rules, where a link was followed. This closes the two-call bypass: `ln -s .e""nv link` in Bash, then `Read ./link`. The resolved form is matched like any other: a rule with `project_relative` (only `deny-prod-config`) sees a path that resolves inside the project (`CLAUDE_PROJECT_DIR`, else the hook's working folder) as the part below the project folder, so a project under a folder named `production` is not denied. That inside test is by text (`~` expanded, joined to the working folder, cleaned, compared with a `/` boundary against the project folder as written and as resolved); links are followed only here, on the named path fields, and a field's resolved path places that field. Every other string (Bash words, MCP strings) is placed by text with no disk call, so large input costs only the text work. With isolation off no link is followed. It only adds denies. Bash is left to the sandbox, which blocks a link to a listed file.
- **Post redaction** (`redact.redact_fields`). Covered in "What happens on one tool call". It is a second check for shaped secrets that the masks do not cover (environment variables, files outside the project), not the control. It reverses the stance "the conversation is never changed", for isolation only.

What the layer does not do is in the README and in THREAT_MODEL ("Isolation (opt-in)" under "Gaps in the rules"). Tested: `tests/unit/test_t014_isolation.py` and the T-014 cases of `tests/e2e/test_hooks_e2e.py` (the plugin's code, on real files), and `tests/live/t014_probe.py` (real `claude -p` sessions with the real sandbox; run by hand after a Claude Code upgrade). On a host with Ubuntu's user-namespace restriction and no AppArmor profile the exact block refuses every shell command (the script shows it, then uses a probe-only `network.allowAllUnixSockets` override in a `--settings` file to show the masks; the shipped block never sets it, and the tripwire denies it in a project file). Not probed: PowerShell and Monitor (the docs say they are sandboxed), macOS, a host with no bubblewrap beyond the start-up refusal, git worktrees.

## Audit and state

- Audit: `${CLAUDE_PLUGIN_DATA}/audit/YYYY-MM-DD.jsonl` (the plugin creates the folders with mode 0700 and the files with mode 0600; an existing folder or file keeps its mode). Each line is written with one `write` call on an append-mode file, which is meant to keep two hooks running at once from mixing lines. This is expected on a local file system and has not been tested with real parallel hooks; the return value of `os.write` is not checked. A short write would leave a partial line. Each line is one JSON object with: `ts` (UTC time), `session_id`, `tool_name`, `tool_use_id`, `event` (`decision` or `result`), `decision`, `rule`, `step`, and `input` (redacted; if longer than `audit.max_input_chars`, default 2000, it is replaced by `{"truncated": "<the first max_input_chars characters of the input as JSON text>"}`). Decision lines also have `reason`. Result lines also have `result_bytes`, `status` (`error` for a PostToolUseFailure event, or when the tool response has `is_error` or `interrupted` set to a true value, otherwise `ok`) and `warnings` (a list; each entry is `{"warning": "prompt-injection-suspected", "marker": <marker id>, "excerpt": <text from the scanned string, redacted, at most 80 characters>}`, or `{"warning": "scan-timeout", "marker": <id of the marker that was running, or null>}`). A result line has `scan_truncated: true` only when the 200000-character cap cut text. `result_bytes` is the UTF-8 size of the response as JSON text. Every line is written with `ensure_ascii`, so it is ASCII: a non-ASCII character appears as `\uXXXX` (`jq` and `json.loads` show the original; `grep` for a non-ASCII word in the raw file does not find it), and a lone surrogate cannot stop the write. Unless `otel_field_names` is false, three more fields are added: `gen_ai.tool.name`, `gen_ai.tool.call.id` and `gen_ai.conversation.id`.
- State: `${CLAUDE_PLUGIN_DATA}/state/<session>.calls` and `<session>.decisions` (the "memo"). `<session>` is the session id with every character other than letters, digits, `_` and `-` replaced by `_` (so `a/b` and `a_b` share files), cut to 80 characters. `.calls` gets one line `{"id": <tool_use_id>}` per call, and the step number is the number of lines. `.decisions` gets one line per call with the fields `id`, `decision`, `rule` and `step`; Post uses the last line whose `id` matches. Pre and Post are separate processes, and these files are how Post learns Pre's decision.
- Known limit: the step counter is not locked. Two parallel calls can get the same number. A lock is not built.
- Known limit: each Pre call reads the session's whole `.calls` file (to count it) and each Post call reads the whole `.decisions` file (to find its line), so the work per call grows with the length of the session. This was not measured. The shared `unknown.calls` and `None.calls` files grow without bound. Cleanup is not built: delete old state files by hand.
- Known limit: if Claude Code sends no `session_id`, every call counts in one shared file, `unknown.calls`, which, like every state file, is never cleaned up (a normal session has its own file, so only the shared files, this one and `None.calls` for a `null` id, carry over between sessions). After 200 calls in total, across all sessions and days, every call with no other rule gets `ask` (the step cap). If it sends no `tool_use_id`, Post cannot tell calls apart and takes the last decision with a null id, which may belong to a different call, so a result line can show the wrong decision.
- Known gap: Pre writes a log line only when it denies or asks. For an allowed call it writes only the memo in `state/<session>.decisions`, so the first log line of an allowed call is the result line that Post writes after the call. An allowed call that never ran, or whose Post script failed, leaves nothing in the log. A failed tool call goes to a separate event, PostToolUseFailure (its input has `error` and no `tool_response`; read from the Claude Code 2.1.318 binary). `hooks.json` registers the Post script for both events, so a failed call gets a result line with `status` `error`. A change that is possible but not made: write a decision line for every call and let Post read it from the log instead of from the memo. That would close this gap. The price is one more log line for every allowed call, and a search of the day's log file (one file per day, shared by all sessions) in place of a small per-session memo. The step counter file would stay.

## Cuts (things not built) and known gaps

### Cuts

- **No spend cap.** A hook input has no cost field. A cap estimated from the session transcript (its path is in the hook input) was not attempted.
- **No injection blocking or rewriting.** A phrase match has false positives, and rewriting tool output means the model sees text that differs from the tool's real output, which the log would not show. Scan and log only: the scan is a record of what came in, not a shield.
- **No OpenTelemetry exporter.** The log uses OpenTelemetry's field names (`gen_ai.tool.name` and two more) so an exporter could read it later. Nothing is sent anywhere.
- **No UI, no dashboard, no server.** A JSONL file you can `grep` and `jq`.

### Known gaps

This subsection lists known gaps, not design choices: a fix is possible and not built, or the thing was not tested.

- **No check of the Claude Code version.** `onFailure` needs 2.1.295 or later. The plugin does not test for it, so a user on an older version gets no warning that the hard fail-safe is missing. No work item is recorded for this.
- **No log or state cleanup or rotation.** One log file per day, one pair of state files per session. Delete old files yourself.
- **No file lock for the counter.** See above.
- **No Windows testing.** No Windows machine was used. The path globs that contain `/` (`*/.ssh/*`, `*/prod/*`, `*/.aws/*`) are not expected to match Windows paths with backslashes; the file-name globs (`.env*`, `*.pem`) may still match. `hooks.json` runs `python3`, which may be missing on Windows: then Pre cannot start (the call should be blocked on 2.1.295 or later, untested; on older versions nothing is checked). CI runs on Linux only.
- **No tests on Python 3.8.** The plugin folder and core are written for Python 3.8 or newer, but only 3.12 and 3.14 were run by hand (the hook scripts and the tests), and CI uses the runner's stock `python3`, whose version is not recorded. The workspace root and the demo need Python 3.9 or newer to run the tests and the demo. The unit tests run under the interpreter of `uv run pytest`; only the hook subprocesses use the runner's stock `python3`.
