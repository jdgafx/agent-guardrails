# Architecture

agent-guardrails is a Claude Code plugin. Claude Code runs a small script (a hook) before and after each tool call; this plugin's scripts check the call against rules in `policy.json`. The first script (Pre) answers deny, ask or allow and logs each deny and ask (a decision line, with exceptions: see "Fail-safe rule"); the second (Post) logs each call that ran (a result line, when the Post script works). This document explains how it is built and why. What it does not protect is in [THREAT_MODEL.md](THREAT_MODEL.md); get started and the front page are in the [README](../README.md) (install options are under "Install options" below); unfamiliar words are in the [GLOSSARY](../GLOSSARY.md).

Short forms used below: **Pre** and **Post** are the two scripts, `hooks/pre_tool_use.py` (runs before the call) and `hooks/post_tool_use.py` (after it). The **data folder** is the folder Claude Code gives the plugin through `${CLAUDE_PLUGIN_DATA}`; it is outside the plugin folder and survives plugin updates (as Claude Code documents it; not tested here), and it holds `audit/`, `state/` and an optional `policy.json` of your own. **Bypass mode** is Claude Code run with permission checks off.

## Problem and goals

- **Problem.** An agent that runs commands and edits files can do something destructive or expose a secret by mistake, and Claude Code is not known to keep a per-call record of what a guard allowed, asked or denied (not checked).
- **Goals.** Deny the commands and file names that `policy.json` lists, in the listed spellings. Ask a person before the commands `policy.json` lists as ask. Keep a redacted log. Tell Claude and the person when a tool result holds injection phrases, and make shell, web and MCP steps ask for the rest of a session that read such text from an outside source.
- **Non-goals.** A spend cap, injection blocking or rewriting, an exporter, a server that runs without you starting it or an always-on service (see "Cuts"), and protection against a determined attacker (see [THREAT_MODEL.md](THREAT_MODEL.md)).

## Overview in full

A Claude Code plugin that checks the tool calls the agent makes, before they run (Claude Code sends each call to the hook).
It denies the file and MCP tool calls its rules list as dangerous, asks you about the ones they list as risky (and about a shell command that matches a deny rule, because shell text can be spelled in ways no rule matches), and writes a log of denies, asks and calls that ran (with gaps: see "Limits of the log" in [THREAT_MODEL](THREAT_MODEL.md#limits-of-the-log)). A call that matches no rule is allowed (apart from the built-in checks: `deny-guard-files`, `ask-guard-paths`, `ask-claude-settings`, `oversize-command`, `step-cap` and `ask-after-injection`). The plugin creates the log with mode 0600, so other users cannot read it; the agent can. "What this does not do" below lists the main known gaps.


## The seven controls

Words used here (hook, policy, step cap, deny, ask, allow, MCP, bypass mode) are defined in [GLOSSARY](../GLOSSARY.md).

| # | Control | What it does | Where |
|---|---------|--------------|-------|
| 1 | Denylist (deny) | Denies `.env` files, private keys, cloud and SSH credentials and production paths when a path field of a file or MCP tool names them. In a shell command, these rules ask instead, and so does the force-push rule (`git push` followed by `--force`, `--force-with-lease`, `-f` or `+branch`; it reads only Bash, not PowerShell or Monitor): see "What holds each threat" in [THREAT_MODEL](THREAT_MODEL.md#what-holds-each-threat). The rules are in one editable `policy.json`. A rule is **deny** or **ask**; deny beats ask; a call that matches no rule is allowed; a Bash command over 20000 characters is not checked and always asks. Option words before the subcommand are allowed (`git -C repo push --force` asks). Gaps (quoted or hidden spellings): see "What this does not do". | `deny-*` rules, `policy.json`, `rules.py` |
| 2 | Approval gates (ask) | Asks you before `git push`, recursive `rm`, `git reset --hard`, `terraform apply` and `destroy`, `kubectl apply` and `delete`, `vercel --prod`, package publish (`npm`, `pnpm` or `yarn publish`, `twine upload`, `cargo publish`, `uv publish`, `gem push`), MCP tools with `send`, `delete`, `post`, `pay`, `charge` or `transfer` at the start of a word of the tool name (`mcp__gmail__send_email`, `mcp__x__bulkDelete` and `mcp__x__make-payment` ask; `mcp__x__get_posts` and `mcp__x__list_payments` do not; the server name does not count), and any Bash command over 20000 characters. Option words may sit before the subcommand (`git -C repo push`, `kubectl -n prod delete`, `terraform -chdir=infra apply`, `npm --tag x publish` all ask). It also asks before `git clean -f`, `gh pr merge`, `gh release create`, `docker push`, `helm install`, `upgrade` and `uninstall`, `find -delete`, a `python -c` one-liner that deletes files, `aws s3 rm`, `cp`, `mv` and `sync`, `aws` operations (the word after the service name, as in `aws ec2 terminate-instances`) starting `delete-`, `put-`, `create-`, `update-` or `terminate-`, and `vercel --target=production`. | `ask-*` rules, `oversize-command` |
| 3 | Audit trail | One JSON line for each deny, each ask, and each call that ran (with gaps: see "Limits of the log" in [THREAT_MODEL](THREAT_MODEL.md#limits-of-the-log)), file mode 0600, under `${CLAUDE_PLUGIN_DATA}/audit/`. | `audit.py` |
| 4 | Step cap | After 200 calls in one session, any call with no other rule switches to **ask**. | `step-cap` rule |
| 5 | Secret redaction | Seven key formats (the AWS secret key only after `aws_secret_access_key=` or `:`, not in the quoted JSON form) are replaced with `[REDACTED:kind]` before anything is written to the log. With isolation on, the same formats are also replaced in the output of a successful shell command before Claude sees it, so that output differs from what the command printed (see "Isolation (opt-in)"). | `redact.py` |
| 6 | Untrusted input | The output of every tool you have not listed in `trusted_tools` (failed calls too) is scanned for six injection phrases (more can be added). On a hit, Claude is told in the same step that the result is data, not instructions, and you see a notice; the result itself is not changed (only the isolation redaction in control 5 changes shell output). A hit from WebFetch, WebSearch or an MCP read tool also marks the session: until it ends, every step except reading and editing local files asks (rule `ask-after-injection`). The scan is a signal, not a shield (what it misses: limits 2 and 3 in [THREAT_MODEL](THREAT_MODEL.md)). | `injection.py`, `hooks.py` |
| 7 | Fail safe | An internal error, bad input or an unwritable state file gives **ask**, not allow, but only for a call no rule denies or asks about: the rules run first, so a deny stays a deny when the data folder is unset, unwritable or a file, or an added policy file is broken. If the hook cannot start, crashes or times out, `"onFailure": "block"` in `hooks.json` should make Claude Code block the call (2.1.295 or later; untested here). See "How the fail-safe works". | `hooks.py`, `hooks.json` |

### How the fail-safe works

The Pre hook runs these steps in order: read the input, check the guard paths (below), load the policy, check the rules, count the call (in `state/`, inside the data folder), save its decision, write the log. The rules run before anything that touches the data folder, so a deny stays a deny and an ask stays an ask when the data folder is unset, a file or read-only. Only a call that no rule matched becomes an ask when it cannot be counted, saved or logged. A shipped policy that cannot load makes every call ask, except the denies on the guard's own files. An added policy file that is missing, unreadable or invalid is left out and the shipped rules still apply (details under "Change the rules").

Three built-in checks guard the guard itself. They compare paths after `~`, `..` and symbolic links are resolved.
- `deny-guard-files`: the Write, Edit, MultiEdit and NotebookEdit tools, and any MCP tool, are denied on a path inside the plugin folder, the data folder or the `GUARDRAILS_POLICY` file. (An MCP tool is denied there even when it only reads; the Read tool is not affected, so you can still read the log with it.) Claude may not edit your policy file either: edit it yourself.
- `ask-guard-paths`: a Bash command asks when one of its words is an absolute or `~` path inside those places, for example `tail ~/.claude/plugins/data/agent-guardrails/audit/x.jsonl` or `sed -i s/deny/ask/ /opt/agent-guardrails/policy.json`. This is a tripwire, not a barrier: see "The agent can still change the guard from the shell" below.
- `ask-claude-settings`: a write tool asks before it changes `.claude/settings.json` or `.claude/settings.local.json` in the project, or the same two files in your home folder (or in `CLAUDE_CONFIG_DIR` when that is set), because those files can switch the plugin off. The `onFailure` setting is on the Pre hook only; its version and test caveat is under "What this does not do".

## Other agents

Claude Code calls the two hook scripts. Every other agent comes in through `guard.py` in the plugin folder (stock `python3`, nothing installed), and all of them end in the same `hooks.run_pre` and `hooks.run_post`: the same rules, redaction, injection scan, session mark and log. `adapters.py` turns each agent's input into Claude Code's shape first, so a tool is always named `Bash`, `Read`, `Edit` or `mcp__<server>__<tool>` when the rules read it.

| Entry | Command | What it sees | A call that would ask |
|---|---|---|---|
| Cursor hooks | `guard.py hook cursor` | `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`; the two after-hooks for the log, the scan and the mark | asks (Cursor's own prompt); a file read is refused, that hook has no ask |
| Codex hooks | `guard.py hook codex` | `PreToolUse` and `PostToolUse` of every tool Codex sends; a patch is checked file by file as an `Edit` | refused |
| Generic JSON | `guard.py hook generic` | `{"tool": ..., "input": {...}}` or `{"command": "..."}` on stdin; the answer is `{"decision", "reason"}` and exit code 0 (allow) or 2 | the caller decides; exit code 2 |
| MCP proxy | `guard.py mcp --name NAME -- <cmd> <args>` | every `tools/call` of one stdio MCP server, and its result (secrets replaced, scanned, a note put in front of a flagged result) | an MCP elicitation to the person when the client offers it, else refused |
| Shell wrapper | `guard.py shell -c "<cmd>"` as `$SHELL` | each `-c` command, then the real shell takes over (`os.execv`) | refused, exit code 126 |

Why an ask is refused in three rows: Codex's hook doc says an `ask` answer fails the hook and the call runs, a `$SHELL` has nobody to ask, and an MCP client without elicitation has no question channel. A refusal is the only answer that is not an allow. The log line keeps the real decision (`ask`) and the rule.

`python3 -m guardrails_dashboard --install <claude|cursor|codex>` does the wiring. For Claude Code it runs `claude plugin marketplace add` and `claude plugin install`. For Cursor and Codex it adds entries to `~/.cursor/hooks.json` or `~/.codex/hooks.json`: other entries stay, a second run changes nothing, the file as it was is kept as `hooks.json.guardrails-bak`, and a file that is not valid JSON is left alone. The hook command names the data folder the dashboard reads, so one page shows every agent; with no Claude Code plugin folder that is `~/.agent-guardrails`. Every log line carries `agent` (`claude-code` when the line does not say). A write tool on one of those two hooks files asks, like a write to Claude Code's settings.

Limits. The Cursor and Codex shapes come from those agents' hook docs; the tests send payloads in those shapes and do not run the live agents. Cursor's own file edits are not checked (no hook is wired for them). Codex must be told to trust a new hook (`/hooks`). The shell wrapper checks only `-c` commands (every word that is not an option, so an option value or a script argument is checked too): a script file, commands on stdin and a program the agent starts without `$SHELL` are not seen. The proxy covers stdio servers only, takes no `tools/call` inside a JSON-RPC batch, drops a line that is not strict JSON, refuses a `tools/call` whose id is not a text or a whole number, and an MCP client that accepts elicitations by itself turns an ask into an allow. An agent that can edit its own config can take the proxy or the wrapper out again.

## NHI and agent discovery

`discovery.py` (`--scan`, `GET /api/inventory`, `guard.py scan`) lists what is on this computer: the agents found (`~/.claude`, `~/.cursor`, `~/.codex`), the MCP servers in their user and project config (`~/.claude.json`, `.mcp.json`, `mcp.json`, `config.toml`), and the NHIs within reach (`.env*` files at the top of the project, `~/.ssh`, `~/.aws`, `~/.kube/config`, `~/.config/gcloud`, `~/.npmrc`, `~/.pypirc`, and the names of environment variables that end in `_KEY`, `_TOKEN`, `_SECRET` or `_PASSWORD`).

It only reads. It never opens a credential file (it reports presence and permission bits) and never reads the value of a variable. Of an MCP server it keeps the name, the program's file name, the host of a URL and the credential-like names of its env vars and headers; arguments, URL paths and values are dropped because they can hold tokens.

The level is the lethal trifecta: (1) outside content comes in through a web tool or an MCP server, (2) a secret is within reach, (3) a shell or an MCP server can send data out. All three is CRITICAL, two is HIGH, fewer is OK; each leg lists what was found for it. Expect CRITICAL for an agent with a web tool and a shell on a developer's computer: that is the finding, not a fault of the scan. The project's own level counts only the project's MCP servers and `.env` files.

Limits. It starts no server, so the classes of a server (`read`, `write`, `exec`, `network`, `financial`) are a guess from its name and command. Connectors that live in an account (claude.ai, ChatGPT) and servers shipped inside plugins are not in those files. Codex's `config.toml` needs Python 3.11 or newer. Only `.env` files at the top of the project are listed.

## Modules (in guardrails-core)

| File | Job |
|------|-----|
| `hooks.py` | The two entry points, `run_pre` and `run_post`, and the `ask` that Pre returns on an internal error. Pre runs the guard check and the rules before anything that can fail (the policy of the user, the data folder). Pre also reads the session mark and, while it is set, asks for every tool outside the local-file list. Post tells Claude and the person when the scan flags a result (`_note_for_claude`, `_notice_for_person`: all hook output text lives here) and writes the mark. With isolation on, Pre also runs the tripwire and Post also redacts shell output. |
| `rules.py` | Turns (tool name, tool input, step) into deny, ask or allow (`match`, `cap`, `evaluate`), and holds the guard check (`guard_paths`, `guard_check`, `stronger`) and the local-tool list `LOCAL_TOOLS` with `after_injection`, the ask for a marked session. `match` takes an optional `cwd`: with it, a path field of a non-Bash tool is also matched in its resolved form (the link check of isolation). The shell-ask rule is its last step: a deny of kind `path` or `command` on a shell tool (`SHELL_TOOLS`: Bash, PowerShell, Monitor) is returned as an ask with the same rule id. |
| `policy.py` | Loads the shipped `policy.json`, checks every policy file against `policy.schema.json` in full, and merges the added policy files into the shipped one. |
| `audit.py` | Writes log lines, counts calls, remembers Pre's decision for Post, and keeps the session mark (`mark_session`, `is_marked`, `first_mark`). |
| `injection.py` | Scans the output of every tool that is not trusted (`trusted_tools`) for injection phrases and reports the hits (`hooks.py` logs them, tells Claude and marks the session); a signal, not a shield. `named_untrusted` says whether an `untrusted_tools` pattern names a tool. It reads the text values of the result (not keys, numbers or base64 data), applies NFKC, removes invisible format characters, collapses white space and keeps the first 200000 characters. Markers match without regard to case. One 3-second timer covers the whole scan (not on Windows or off the main thread). |
| `redact.py` | Replaces known secret formats (seven patterns; the names are under "Audit log format" below) with `[REDACTED:kind]`. `redact_fields` does it for chosen keys of a dict (used for shell output with isolation on). |
| `adapters.py` | Turns the hook input of Cursor, Codex or a generic caller into Claude Code's shape, runs it through `hooks.py`, and shapes the answer for that agent (`normalize`, `check`, `answer`). |
| `mcp_proxy.py` | The stdio proxy in front of one MCP server: checks `tools/call`, asks through elicitation, redacts and scans results. |
| `shell_guard.py` | The `$SHELL` wrapper: checks and logs a `-c` command, then `os.execv` of the real shell. |
| `discovery.py` | The read-only NHI and agent inventory and its lethal-trifecta level. |
| `install.py` | Wires the guard into Claude Code (its plugin commands), Cursor and Codex (their `hooks.json`). |
| `isolation.py` | The opt-in isolation layer: `sandbox_block` generates the Claude Code sandbox settings block from the secret rules, `block_in_force` checks that a project's settings files hold it and open no sandbox write path or host, and `python3 -m guardrails_core.isolation <policy.json>` prints the block (`make isolation`). |

## What happens on one tool call

Claude Code runs one hook before a tool call (the `PreToolUse` event) and one after the call finishes (the `PostToolUse` event).

```text
Claude wants to run a tool
        │
        ▼
PreToolUse hook  (hooks/pre_tool_use.py → guardrails_core.hooks.run_pre)
  1. read JSON from stdin and check it
  2. guard check: a write tool (or any MCP tool) on a guard path is deny, rule "deny-guard-files"; a write tool on one of the four Claude Code settings files (or the two in `CLAUDE_CONFIG_DIR`) is ask, rule "ask-claude-settings"; a Bash command with a word that is an absolute or ~ path inside a guard path is ask, rule "ask-guard-paths"
  3. load policy: the shipped policy.json in the plugin folder, then the file named by the GUARDRAILS_POLICY environment variable, then <data folder>/policy.json, each added file checked against the schema and merged in (it can only add; `trusted_tools` is the one key that turns something off: the log warning and the note to Claude); an added file that fails is left out and its error kept; a shipped policy that fails ends the call with ask (a guard deny from step 2 stands)
  4. if a Bash command is over 20000 characters: ask, rule "oversize-command", and skip the rules
  5. check every rule, whatever its kind (path, command or tool name); strongest wins (deny beats ask; the guard result of step 2 wins a tie). A deny of a path or command rule on Bash, PowerShell or Monitor is returned as ask, with the same rule id and a note in the reason (the shell-ask rule); a tool rule and every other tool name keep the deny. With isolation on (`"isolation": true` in an added policy file), step 5 adds two checks: the link check (a path field of a non-Bash tool is also matched as resolved, so `Read` on a link to `.env` is denied) and, for Bash, PowerShell and Monitor, the tripwire (deny, rule "isolation-not-active", when the sandbox block is not in force in the project's `.claude/settings*.json`; see "Isolation (opt-in)")
  6. if no rule matched and an added policy file was left out: ask, rule "guardrails-policy-error", with the file and the error
  6b. read the session mark (the size of state/<session>.taint, in its own try): if it is set, every tool outside `LOCAL_TOOLS` is ask, rule "ask-after-injection", merged with the stronger-wins rule (a deny stays a deny; on a tie the shipped rule keeps its id); if it cannot be read, ask, rule "guardrails-error"
  7. count the step (state/<session>.calls); an allow that cannot be counted becomes ask, a deny or ask stands
  8. if no rule matched and step > cap: ask, rule "step-cap"
  9. remember decision, rule and step (state/<session>.decisions)
 10. deny/ask: write a "decision" audit line, print the JSON answer
     allow: print nothing
        │
        ▼  (Claude Code acts on the answer; see the note below)
        │
PostToolUse hook (hooks/post_tool_use.py → run_post)
  1. read JSON from stdin and load the policy (as Pre does, with the added policy files; a failure of the shipped policy ends the call with an error and no log line)
  2. with isolation on and the tool Bash, PowerShell or Monitor: replace known secret formats in the `stdout` and `stderr` strings of the response (`redact_fields`)
  3. unless the tool is trusted (`trusted_tools`; `untrusted_tools` wins over it) scan the output (for a failed call, its error text) for injection phrases; this needs no data folder
  4. when there are hits and an `untrusted_tools` pattern names the tool: write the session mark (one line in state/<session>.taint, in its own try)
  5. in one try: check the data folder is set (an unset one means no log line), look up what Pre decided for this tool_use_id, and write a "result" audit line (redacted, with any warnings, `warned` and `tainted`; it uses the original response)
  6. print nothing, except in two cases: the scan had hits (print one JSON object with `additionalContext`, the note to Claude, and `systemMessage`, the notice to the person), or step 2 changed the output (the same object also holds `updatedToolOutput`). A step 4 or 5 error goes into `systemMessage` when there is something to print and exits 0; with nothing to print it is raised and the script exits 1. The result is never replaced except by the redaction.
```

Between the two hooks, Claude Code enforces deny, asks you on ask, and on allow carries on with its own normal permission prompts. This is Claude Code's documented behaviour and is not tested here; for bypass mode see limit 5 in [THREAT_MODEL.md](THREAT_MODEL.md).

### Hook input and output

Both hooks read one JSON object from standard input. It must have a non-empty text `tool_name`. If `tool_input` is present it must be an object. Pre also reads `cwd` (the folder Claude Code runs in, which it sends with every hook call per its hook docs; not tested here) to resolve relative paths in the guard check; if it is missing or not text, the hook's own working folder is used. `session_id` is optional (a missing one becomes `"unknown"`; an empty one also counts in `unknown.calls`, but the log keeps it empty), `tool_use_id` is optional (a missing one means no id), and Post also reads `hook_event_name` and `tool_response` (a PostToolUseFailure input has no `tool_response`; Post then scans and measures its `error` text). Pre prints nothing for allow. For deny and ask it prints one JSON object: `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny" or "ask", "permissionDecisionReason": "[rule-id] reason text"}}`, and it exits 0 on every path the wrapper covers (a failed import is covered; a crash outside the wrapper is not). A `session_id` that is JSON `null` is not replaced by the default: the call counts in a file named `None.calls`. Post prints nothing when the scan found nothing; it exits 0 when its log line was written and 1 when it was not (Claude Code documents 1 as a non-blocking error; not tested here). When the scan found a marker it prints `{"hookSpecificOutput": {"hookEventName": <the input's hook_event_name>, "additionalContext": <the note to Claude>}, "systemMessage": <the notice to the person>}`. `additionalContext` is the field the Claude Code hooks documentation names for adding context; it is valid for PostToolUse and PostToolUseFailure. The note names the tool and the marker ids and never quotes the matched text, and the result stays as it was (`decision: "block"` was not used: the call has already run). When Post changed shell output with isolation on, the same object also holds `updatedToolOutput` (the response with stdout and stderr redacted). A failed log or mark write is appended to the `systemMessage` as "guardrails audit failed: ..." and the script exits 0.

## Fail-safe rule

Each failure has one owner. Layer 1 is the hook script itself. Layer 2 is Claude Code, for failures where the script cannot run at all.

### Layer 1, inside the script (answer: ask)

`PreToolUse`: the rules run before anything that can fail, so a deny stays a deny. The step numbers here are those of the diagram above. If Python runs but the import of the vendored core fails (a missing `vendor/` folder), the wrapper in `pre_tool_use.py` catches that and asks. Inside the engine:
- An exception in step 1 (bad input) gives `ask` with a `guardrails-error` reason and exit code 0, and a log line when the data folder can be written (tool name `unknown` and an empty input when the input could not be read).
- The guard check (step 2) needs no file in the data folder, so it runs first. If the shipped policy then cannot be loaded (step 3), a guard deny (a write tool on a guard path) still stands and is logged when the data folder can be written; any other call gets `ask` with a `guardrails-error` reason, even `cat .env`. This is the one case where a would-be deny is an ask, and the price of not having a built-in minimum deny list.
- An added policy file that cannot be read or fails the schema does not stop the rules: it is left out, the shipped rules run, and a call that no rule matched gets `ask` with rule `guardrails-policy-error` naming the file and the error. That ask is a real decision: it is counted, saved in the memo and logged.
- An unset data folder, a data folder that is a file, or a read-only `state/` stops only the counting and the logging (steps 7, 9 and 10). A deny or ask from the rules stands. A call that no rule matched is an allow that cannot be counted, so it becomes an ask with a `guardrails-error` reason.
- An exception in step 9 or 10 (save the decision memo `state/<session>.decisions`; write the log line, deny and ask only) comes after the rules ran: a deny stays a deny, an ask stays an ask, and an allow becomes an ask, because an allowed call whose memo failed would otherwise go unrecorded. (If nothing could be written, Post's own result line, when it succeeds, shows decision `unknown`.) The memo and the log line are tried separately, so a failed memo no longer loses the log line of a deny or ask.
An `ask` caused by an internal error (a `guardrails-error` reason) is logged like any other decision: Pre writes a decision line and a memo with rule `guardrails-error` when the data folder can be written (the helper the guard-deny fallback uses; for input it could not read, the line has tool name `unknown` and an empty input, and the raw text is not logged). The ask does not depend on the write: when nothing can be written, and the user approves the call and the Post script works (it reads the shipped policy and the data folder too), Post finds no memo and writes decision `unknown`, rule and step null.

### Layer 2, in Claude Code (answer: block)

Layer 1 cannot run if Python never starts or the hook is killed. By default, Claude Code lets the call go ahead when a PreToolUse hook can't start, times out, or exits with an unexpected code (not 0 or 2). Exit 0 means success; exit 2 is the code a hook uses to block a call. So `hooks.json` sets `"onFailure": "block"` on the PreToolUse hook (Claude Code 2.1.295 or later). Then a missing `python3`, a crash outside the wrapper, or a timeout should block the call. On an older Claude Code those cases probably fail open, but this was not tested: an older version might instead reject the hook entry, and then the guard would not run at all (limit 9 in [THREAT_MODEL.md](THREAT_MODEL.md)). Source: the Claude Code 2.1.295 release note, "Added `onFailure: "block"` for command and HTTP hooks: a hook that can't start, times out, or exits with an unexpected code blocks the action instead of letting it through." No link to the note was recorded. The block itself and the timeout are not tested here, and this whole layer rests on that note.

### Slow input

Regex time grows with input size, and a timed-out hook is a failure of layer 2. Post also runs user-supplied regexes (the injection markers, on up to 200000 characters) under the same 10-second timeout with no `onFailure`: a Post timeout loses that call's result line and blocks nothing. The scan guards against that. The shipped markers use only bounded repeats (`\s{1,3}`, `{0,60}`), white space is collapsed to one space before they run, and the whole scan runs under a 3-second timer (`signal.setitimer`; Linux and macOS, main thread): when it fires, the warnings found so far stay, the line gets a `scan-timeout` warning that names the marker, and the line is still written. Without a timer (Windows, or off the main thread) a slow marker, shipped or added, can still run into the 10-second timeout; the shipped markers are tested at under 1 s each on 21 repeated inputs of 200000 characters (`test_case_35_every_marker_is_fast_on_every_seed`). Two measures, with different jobs. The size cap carries the load: the rules never see a Bash command over 20000 characters; it gets `ask` with rule `oversize-command`, so a deny pattern inside a huge command becomes an ask. The shipped regexes were also rewritten to avoid the slow case, as a second line. With the cap switched off in a test (`test_regexes_scan_in_linear_time` sets the constant `MAX_COMMAND_CHARS` in `rules.py` very high), the test runs three repetitive inputs of 60 to 180 KB (`rm `, `git push `, `vercel `, each repeated 20000 times and followed by `; cat .env`) and asserts that each finishes in under 5 s with the answer still deny. A hand measurement of the `rm rm rm ...` case gave 0.2 s (it took 23 s before the regexes were rewritten; the test comment records this). Python's `re` can backtrack, so this is a measurement on these shapes, not a proof. Redaction runs on the whole tool input before the log cut, and the cap does not cover it; timed by hand on one Linux machine it took 0.2 s on 5 MB of plain text and 0.1 s on 3 MB after `Bearer ` (no test). The 20000 limit is that constant in `rules.py` and cannot be set in `policy.json`. The 200-call step cap is `step_cap.max_calls` in the shipped `policy.json`. The 10-second hook timeout is set in `hooks.json`.

### Why ask, and what is not built

Why ask and not deny on an internal error? A broken guard should not stop all work: an ask lets a person continue, while a deny on every error would stop every call. (It keeps a human in the loop only when someone can answer: not in `claude -p`, limit 6, and not in bypass mode, limit 5.) Layer 2 cannot show a prompt: the setting the release note describes is `onFailure: "block"`, not an ask. So a missing `python3` should stop every call until the user fixes it (on 2.1.295 or later; see layer 2).

Counting the step after the rules is built (T-007): the rules run first, so a full disk or an unwritable data folder no longer turns a deny into an ask. One alternative is not built. It is deferred, not rejected: no technical blocker is known and no reason beyond priority is recorded. A built-in minimum deny list would apply when the shipped policy cannot load; it is not built, has no work item, and would be a second set of rules that must agree with `policy.json`. The price today is that a missing or broken shipped policy turns every call, except a guard deny, into an ask.

## Decision: vendoring, not a pip install

The hook runs as `python3 hooks/pre_tool_use.py` on whatever `python3` the user has. A plugin install is expected to be a plain folder copy. Not checked: whether `/plugin install` runs any package-manager step.

So the plugin cannot depend on a package from the workspace. Options considered:

| Option | Why not |
|--------|---------|
| `pip install guardrails-core` at install time | A plugin install is expected to copy the folder with no package-manager step (not confirmed; see above). It would also need network access, which the README says the hooks do not use. |
| A venv inside the plugin | Not portable between machines: a venv holds absolute paths and compiled files for one machine. |
| A `SessionStart` hook that builds the code in the data folder | Not built: it adds a start-up step that can fail before the guard exists, and the committed copy needs none. |
| One big file written by hand | Hard to test and review as one unit. |
| One big file generated from core and drift-checked like `vendor/` | Would work. Not chosen: it is the same copy-and-check idea with a harder file to read in a diff. |
| A symlink or a git submodule to core | Not used: a link that points outside the plugin folder may not survive an install that copies the folder (not checked), and the committed copy needs no such assumption. |
| Put all the code inside the plugin folder (no separate core package, no copy) | Would work with no copy and no drift check. This is a scope decision, not a technical one: the brief for this project (not in this repo) asks for a core package, a plugin and a demo (the acceptance test `tests/acceptance/test_t001_done.py` checks that those folders exist). The price is the two gaps below. |
| **Vendor core into the plugin** | Chosen. `make build` deletes `packages/guardrails-plugin/vendor/guardrails_core/` and copies `guardrails-core/src/guardrails_core/*.py` into it (a hand edit in `vendor/` is lost; a file deleted from core disappears from `vendor/` too). It makes two more copies the same way: `__init__.py` and `server.py` of the dashboard into `vendor/guardrails_dashboard/`, and the root `index.html` into `vendor/index.html`. The hook adds `vendor/` to `sys.path`. |

The vendored copy is **committed**, so `claude --plugin-dir` works from a fresh clone with no build step. Two checks look for a stale copy, and each has a gap:
- A unit test compares every vendored file byte for byte with its source (core, the two dashboard files and the page). `make test` runs `make build` first, which refreshes the copy, so under `make test` this test cannot fail. It can fail only when you run `pytest` directly.
- CI runs `make build` and then fails if `git status --porcelain` lists anything under the vendor folder, new untracked files included (before T-009 it ran `git diff`, which ignores files git does not track yet), so a new core module whose vendored copy was never added to git fails CI instead of reaching a fresh clone. There its import would fail and every call would get `ask`. A local `make test` runs `make build` first, so it cannot see drift; CI runs the check before `make test`. After `make build`, run `git status` and add new files.

Cost: two copies of the same code in git, and the CI gap above. Gain: the plugin needs only `python3` on PATH and no install step.

## Decision: the dashboard ships in the plugin (T-037)

T-032 kept server code out of the plugin: the server was never copied into it, and an install would have carried an unused server. That reasoning is reversed. A person who installs from the marketplace has no clone, so the copy inside the install is the only way for them to run the dashboard, and the code is used. It runs only when the person starts it (`dashboard.py`, from the start command in the README), on 127.0.0.1, behind the one-time key.

How the install picks what it shows:
- Claude Code keeps old version folders on disk. The copy that serves is the one named in `installed_plugins.json` (key `agent-guardrails@agent-guardrails`; the file's format is Claude Code's, not documented, and only the parts the tests use are read). A copy the start command reached first hands over to it, so one version runs from start to end.
- Only a version folder of this plugin's own cache folder is ever run. A record that names any other place, or a file in a shape the code does not know, gives a warning and the started copy's policy, not an exit.
- The log is read from the data folder Claude Code gives that install (`plugins/data/agent-guardrails-agent-guardrails`), never from another install's folder.
- If the version in force is older than 0.2.0 it does not carry the dashboard, and the command says to update instead of showing rules that are not in force.

The cost: about 150 KB more in the plugin folder, and code that an agent could replace in the other version folders (see limit 7 in [THREAT_MODEL.md](THREAT_MODEL.md)).

Dashboard: with the plugin installed, start it as "Get started" in the [README](../README.md) says. From a clone, run `make dashboard`, then open the link it prints (`http://127.0.0.1:8765/?key=...`) to see your real rules and log; press Ctrl-C to stop it. ## How this relates to Claude Code's own controls

Claude Code has two built-in controls that overlap with this plugin. The first is permission rules in its settings (`permissions.deny` and `ask`). They run inside Claude Code, need no Python and do not depend on a hook timeout. The second is a Bash sandbox that limits, at operating-system level, what shell commands can read, write and reach on the network. The sandbox can limit what a script reads, depending on its settings; this plugin only sees `python script.py`, not what is inside. The plugin's opt-in isolation layer uses the sandbox's read masks for the secret list (tested live; see "Isolation (opt-in)" below); the sandbox's defaults and its use as a write barrier were not tested. It is also the barrier meant for Bash writes to this plugin's own files (limit 7 in [THREAT_MODEL.md](THREAT_MODEL.md)): `sandbox.enabled` true, `sandbox.allowUnsandboxedCommands` false (Claude Code then ignores `dangerouslyDisableSandbox`), `sandbox.filesystem.denyWrite` on the plugin folder and the data folder, and `permissions.deny` rules such as `Edit(//path/to/folder/**)`. The setting names were read from the current Claude Code docs on 2026-11-04; the write settings (`denyWrite`, `permissions.deny` on the guard's folders) were not run against the plugin. The sandbox writes only to the working folder by default, so it does not cover a plugin folder inside the project.

This plugin does not replace them. What it adds, over `permissions.deny` and `permissions.ask`, is a reason shown with each ask or deny, one policy file that installs as a plugin, and an audit log. The two can work together. A Claude Code release note reportedly states that a `permissions.deny` rule wins over a hook that answers `ask`. The version and the exact text were not recorded here and are unverified. Check the release notes yourself; if it holds, put the few things that must never run in `permissions.deny` and use this plugin for the ask tier and the log. This plugin does not depend on that change. Whether a plugin can ship permission settings itself has not been checked, so a user who wants `permissions.deny` must add it by hand.

## Other choices

In one line each:
- Denylist, not allowlist: an allowlist blocks every command that is not listed, so each command the agent needs must be added first. The cost is that every command not on a list runs (see the limits in THREAT_MODEL.md).
- Ask, not deny, on an internal error: explained under "Fail-safe rule".
- Added policy files merge into the shipped one and can only add (`trusted_tools` turns off only the injection scan: its log warning and the note to Claude), instead of one file replacing the other: a replacement can loosen a rule, so the agent (or a typo) could switch the shipped rules off. The cost is that a user cannot loosen a shipped rule from their own file; an `extends` field that let an added rule replace a shipped one was rejected for the same reason.

## Policy

- `policy.json` has `version` (must be `1`), `isolation` (true or false, default false; the opt-in isolation layer), `rules`, `step_cap`, `untrusted_tools`, `trusted_tools`, `injection_markers` and `audit` (the log settings `max_input_chars` and `otel_field_names`).
- Only `version` is required at the top level, so an added file can hold just `{"version": 1, "isolation": true}`. The shipped policy must also have `rules` and `step_cap.max_calls`. When `rules` is present it must not be empty, and rule ids must be unique. A rule has an `id`, a `decision` (`deny` or `ask`; `allow` is not a rule decision), a `kind`, `match` patterns (a non-empty list of text) and a `reason` (all required), and an optional `except` list that only `path` rules read:
  - `path`: glob patterns on every string of the tool input, at any depth and inside lists, dict keys included, except the text fields in `TEXT_FIELDS` in `rules.py` (the text that built-in tools write, search for or send: Write `content`, Edit `old_string` and `new_string`, Grep `pattern`, WebFetch `url` and `prompt`, SendMessage `message`, TaskCreate `description`, and so on; the table lists the built-in tools seen on 2026-11-05, and a tool or prose field missing from it is checked in full, so it can cause a visible deny, never a silent allow). Each string is matched whole. For a Bash command, also on every word of the command, not only words that look like paths; words are split on any white space (spaces, tabs, line breaks) and on `; & | < > = ( ) " '` and the backtick. A glob without a `/` matches the file name only. A glob with a `/` matches the whole path (with a `/` put in front, so `*/.ssh/*` also matches `.ssh/id_rsa`), or on a rule with `project_relative` the part below the project folder (see "Change the rules" below; `rules.path_hit` picks the form, `rules._below` computes it by text, with no disk call). Matching ignores upper and lower case. Each string is tried as written, with a leading `~` expanded, and with `/./`, `//` and a trailing `/` removed (`os.path.normpath`). `except` globs excuse a match. The guard check reads only the named path fields (`file_path`, `path`, `notebook_path`).
  - `command`: regular expressions on the Bash command, found with `re.search`, so they are not anchored. Case-sensitive. Applies only when the tool is named exactly `Bash`; a command run through any other tool gets no command rule, and its string is matched whole against the path rules (`cat .env` through PowerShell or Monitor asks, through another tool name it is denied, and a string that ends in `.env.local` is allowed; see limit 4 in [THREAT_MODEL.md](THREAT_MODEL.md)). `except` is ignored here, with no message.
  - `tool`: regular expressions on the tool name. Case does not matter. `except` is ignored here too.
- If several rules match, deny beats ask. Among rules of the same strength, the first one in the file is the one reported.
- `untrusted_tools` patterns are regular expressions on the tool name and are case-sensitive (the shipped MCP pattern starts with `(?i)`, so MCP names match in any case). `trusted_tools` patterns work the same way. Post scans a call unless a `trusted_tools` pattern matches the tool name and no `untrusted_tools` pattern does. The shipped policy has no `trusted_tools`, so every tool is scanned, tools that do not exist yet too. An added file may set `trusted_tools`: it is the one key that turns something off, and what it turns off is a log warning, never a deny or an ask.
- `policy.schema.json` is the JSON Schema, and it is enforced. `validate(p, schema)` walks the whole of `policy.schema.json` with a small checker (about 30 lines, no `jsonschema` package, because the plugin runs on the stock `python3` with no install step). It knows the keywords the schema uses (`type`, `required`, `properties`, `additionalProperties: false`, `items`, `enum`, `const`, `minItems`, `minLength`, `minimum`), skips the annotations `$schema`, `title` and `description`, and refuses any other keyword, so a later schema edit cannot add a check that does nothing. A JSON `true` is never an integer, and `const` and `enum` compare the type as well as the value (`true` and `1.0` do not equal `1`). After the walk it checks that rule ids are unique within a file and that every regex compiles. So a text `except`, an unknown key such as `step-cap`, a missing `max_calls`, a `max_input_chars` under 100 and a text `untrusted_tools` are all errors. Two things stay outside the schema: that `except` is on a `path` rule (on a `command` or `tool` rule it passes and does nothing; the schema allows it), and that the shipped policy has `rules` and `step_cap.max_calls` (the shipped policy must have them; the schema does not require them).
- Merge: the added rules are appended after the shipped rules (an added rule equal to a shipped one is skipped); `step_cap.max_calls` is the smaller of the shipped and added values; `untrusted_tools`, `trusted_tools` and `injection_markers` are the union; `isolation` is true once any file says true (an added file cannot turn it off); `audit` in an added file is ignored. The shipped rules come first and the rule loop stops at the first deny, so a slow regex in an added file cannot delay a shipped deny on a file tool or a tool rule. A shell text rule only asks and an ask does not stop the loop, so a slow regex in an added file can delay a shipped shell ask.
- `validate()` checks that a pattern compiles, not that it is fast. A pattern you add can be slow enough to hit the 10-second hook timeout. On Claude Code 2.1.295 or later the call should then be blocked (layer 2, untested); on older versions it probably runs unchecked (untested).

## Change the rules

The rules live in `policy.json` (the shipped copy is `packages/guardrails-plugin/policy.json`; it holds the patterns and the step cap of 200). Six checks are built into the code, not into `policy.json`: `deny-guard-files`, `ask-guard-paths` and `ask-claude-settings` (see "How the fail-safe works"), `oversize-command` (the 20000-character limit is a constant in `rules.py`), the `step-cap` ask itself (only its number, `step_cap.max_calls`, is in `policy.json`) and `ask-after-injection` (while a session is marked, every tool outside the local-file list in `rules.py` asks; see "The session mark" in [THREAT_MODEL](THREAT_MODEL.md#the-session-mark)).

The shipped policy always loads first. Your own policy files are added to it, and they can only add, with one exception: `trusted_tools` turns off the injection scan for the tools it names (what it turns off is the log warning and the note to Claude, never a deny or an ask):
1. The file named in the `GUARDRAILS_POLICY` environment variable (set it in the environment that starts Claude Code; use an absolute path).
2. `${CLAUDE_PLUGIN_DATA}/policy.json`.

Both are optional and both are used if both exist. A missing or broken added policy file is left out, the shipped rules still apply, and calls no rule matches ask. The ask names the file and the error (rule `guardrails-policy-error`) until you fix or remove the file. A `GUARDRAILS_POLICY` that names a missing path or a folder counts as broken; no file at all in the data folder is normal. A file in the data folder that is a folder, a dangling link or a pipe is broken too.

What an added file can do:
- Add rules. Shipped rules run first; the strongest rule that matches wins (deny over ask). An added rule cannot weaken or remove a shipped one, and it cannot turn a shipped deny into an ask. An added deny rule of kind `path` or `command` asks on a shell command, like the shipped ones; a `tool` rule still denies. To relax a rule you must edit the shipped file by hand (a plugin update undoes that edit).
- Lower the step cap with `step_cap.max_calls`. A higher value is ignored.
- Add `injection_markers`: more phrases are looked for in the scanned output. Every tool is scanned already; an added `untrusted_tools` name scans nothing new. It stops a `trusted_tools` pattern from turning the scan off for that tool, and it makes a hit from that tool mark the session.
- Add `trusted_tools` names (regular expressions on the tool name): the output of a matching tool is not scanned for injection phrases. This is the one key that turns something off, and what it turns off is the log warning and the note to Claude, never a deny or an ask. A tool that `untrusted_tools` names (WebFetch, WebSearch, MCP read tools) is scanned even if a `trusted_tools` pattern matches it.
- Set `"isolation": true` to turn the isolation layer on (see "Isolation (opt-in)"). A file with only `{"version": 1, "isolation": true}` is valid (`rules` is not required in an added file). `true` in any file wins; no file can turn it off.
- `audit` keys in an added file are ignored: a smaller value would weaken the log.

You no longer need a full copy of the shipped file, only your added rules. If you made a full copy earlier, it still loads (its rules sit beside the shipped ones), but a copy that fails the check below is left out. An old full copy also brings back the old `deny-prod-config` without `"project_relative": true`, which is matched on the whole path: in a project under a `prod` or `production` folder its files are denied again. Delete the copy, or add the field to that rule in it.

[`policy.schema.json`](../packages/guardrails-plugin/policy.schema.json) describes the format, and the hook checks every policy file against all of it: wrong types, unknown keys, a `version` other than the whole number 1 (`true` and `1.0` fail), a text `except`, an empty `rules` list. The shipped policy must also have `step_cap.max_calls`.

To add a rule:
1. Write `${CLAUDE_PLUGIN_DATA}/policy.json` (or keep the file anywhere and point `GUARDRAILS_POLICY` at its absolute path) with `{"version": 1, "rules": [...]}`. Claude cannot write these files for you: the write tools are denied there, so edit them yourself.
2. A rule has an `id`, a `decision`, a `kind` (`path`, `command` or `tool`), `match` patterns and a `reason`, and, for `path` rules only, may have an `except` list that excuses matches, and an optional `"project_relative": true` (a boolean; any other value makes the file invalid). Without it a glob is matched against the whole path. With it, a path that sits inside the project is matched on the part below the project folder, so a rule about `*/production/*` does not fire on a project that lives in or behind a folder of that name. The project folder is `CLAUDE_PROJECT_DIR`, else the hook's working folder. The inside test is by text only, with no disk call: the path with `~` expanded, joined to the hook's working folder and cleaned (`..` folded away), compared with a `/` boundary against the project folder as written and as resolved, never a text prefix. So `~/prod/app/src/x.py`, `../src/x.py` and `/home/u/prod/app/src/x.py` get one answer. A path outside the project, or a `..` that leaves it, is matched whole, as written. **Links:** with isolation on, the path fields of file tools (`file_path`, `path`, `notebook_path`, Glob `pattern`) are also resolved, so a project file that links out to a production folder is denied. A link inside the project named `production` is denied like a folder of that name, in both modes. With isolation off no link is followed (the one stated limit): such a link out is allowed. For a project that sits under a `prod` or `production` folder (`/srv/production/app`) that is weaker than before this rule, which denied every path there because the whole path held the folder name; for any other project it is as before. Shell words and MCP strings are never resolved in either mode. Only `deny-prod-config` carries it; the secret-file rules do not, so a project rooted at `~/.ssh` still has `id_ecdsa` denied. The price: a project rooted at a production config folder itself (`CLAUDE_PROJECT_DIR=~/infra/prod`) has its own files allowed by this rule, because the rule cannot tell that folder from a project that merely sits under one. Keep production config in a sub-folder of the project (`config/production/`), where it stays denied. On a `command` or `tool` rule `except` is ignored without a message; change its `match` pattern instead. Rule ids must be unique within a file. A `deny` there asks when the call is a shell command (Bash, PowerShell or Monitor), so a respelled command is not refused.
3. The policy is read on every hook call, so the change takes effect at once. If the file is wrong, the next call that no rule matches asks and says why.

A new regex is checked to compile, not to be fast, and the hook times out after 10 seconds. The shipped rules come first and the rule loop stops at the first deny, so a slow regex in your file cannot delay a shipped deny on a file tool or on a tool rule. A shell text rule only asks, and an ask does not stop the loop, so a slow regex in your file can delay a shipped shell ask past the timeout; on Claude Code 2.1.295 or later a call that times out should be blocked (older versions probably let it through; untested, see "How the fail-safe works"). It can delay any other ask or an allow past the timeout too. Deleting your policy file removes its rules with no message. Changing the 20000-character limit means editing core and running `make build`.

Release note for upgrades: check your own policy file against the schema. A copy that breaks the strict check (for example a `$schema` key added for an editor) is left out, and calls no rule matches ask until you fix it.

Release note for upgrades: a tool you added to `untrusted_tools` now marks the session when its output is flagged, and a flagged result now sends a note to Claude and a notice to you.

Release note for isolation users: if a project's settings files (`.claude/settings.json` or `.claude/settings.local.json`) hold `sandbox.filesystem.allowWrite`, `sandbox.network.allowedDomains` or a `WebFetch(domain:...)` allow rule, Pre now refuses every shell call there after the upgrade. To get the shell back, move that rule to your user settings (`~/.claude/settings.json`), which Pre does not check and which applies to every project, then remove it from the project file.

## Trust boundary

The guard trusts the files it is made of, and protects some of them. Protected against the write tools (Write, Edit, MultiEdit, NotebookEdit and any MCP tool, rule `deny-guard-files`): the plugin folder (the shipped policy, the hook scripts, `vendor/`, `hooks/hooks.json`), the data folder (`state/*.calls`, `state/*.decisions`, `audit/*.jsonl`, an added `policy.json`) and the file named by `GUARDRAILS_POLICY`. The guard paths are known only at run time, so the check is code in `rules.py`, not a pattern in `policy.json`. Each path goes through `~` expansion, is joined to the hook input's `cwd`, and goes through `os.path.realpath`; a path is inside a guard path when it equals a guard file or equals or starts with a guard folder plus `/` (so `<data>2/x` is not inside `<data>`). A link in the project that points into the data folder is caught. Not protected: anything a Bash command writes without naming a guard path as an absolute or `~` path (limit 7 in THREAT_MODEL.md), Claude Code's own settings files beyond an ask (`ask-claude-settings`, four files), and the Python start-up files of the `python3` the hook runs.

Policy loading, in order; the shipped policy always loads first and added files can only add (`trusted_tools` aside):
1. The `policy.json` in the plugin folder. It must load, pass the schema and have `step_cap.max_calls`, or the call asks.
2. The file named by the `GUARDRAILS_POLICY` environment variable, if the variable is set and not empty. If that path does not exist or is a folder, it is an error: the file is left out and the ask names it.
3. `${CLAUDE_PLUGIN_DATA}/policy.json`, if the data folder is set and anything exists at that path (a link counts as existing). It survives plugin updates. Anything there that is not a regular file (a folder, a dangling link, a pipe) is an error. A path that does not exist is not an error: that is the normal case.

An added policy file can only add to the shipped one (`trusted_tools` aside). A missing or broken added policy file is left out, the shipped rules still apply, and calls no rule matches ask, with the file and the error in the reason. Deleting an added file removes its rules with no message. After updating the plugin, check your policy file against the schema; you no longer need a full copy of the shipped file.

## Isolation (opt-in)

Goal: close the shell forms that no rule can match (a built name, a glob, a parent folder, a link made before the call) for the listed secret files, by isolation and not by more matching. The plugin builds no sandbox of its own. It generates a settings block for Claude Code's Bash sandbox and adds two checks and one redaction. It is off by default (`"isolation": false`); "Isolation from the user's side" below has the user-facing table and the costs.

- **The block** (`isolation.sandbox_block`). Input: the `match` and `except` globs of the first rule with each id in `ISOLATED_RULES` (`deny-env-files`, `deny-credential-dirs`) in the shipped policy; added rules never change it (`test_case_35_added_policy_files_do_not_change_the_block`). Each glob loses a leading `*/` and a trailing `/*` and is written under three anchors: `./**/` (anywhere in the project), `~/` and `~/.config/`. Output: `sandbox.filesystem.denyRead` (39 entries) and `allowRead` (the `except` globs, 9 entries), and `enabled`, `failIfUnavailable` and `allowUnsandboxedCommands: false`, and `autoAllowBashIfSandboxed: false` (so Claude Code's own prompts and allow rules work as before). It never writes an entry that starts with `~/**` or `/**`: on a 4.5-million-file home folder each sandboxed command took 100 to 187 seconds with `~/**/` entries. The committed `isolation/settings.local.json` must equal the generator's output (`test_case_34_block_comes_from_the_secret_list_and_matches_the_committed_file`); `make isolation` rewrites it.
- **Where the block goes.** In the project's `.claude/settings.local.json` (or `.claude/settings.json`): only in project and local settings does `./` mean the project root. A plugin cannot ship sandbox settings (its `settings.json` keeps only `agent` and `subagentStatusLine`), so the user copies the file.
- **The tripwire** (`isolation.block_in_force`, called from `hooks.run_pre`). For Bash, PowerShell and Monitor calls with isolation on, Pre reads `.claude/settings.json` and `.claude/settings.local.json` of `CLAUDE_PROJECT_DIR` (or the hook's `cwd`), merges them as Claude Code does (a boolean from the local file wins, lists are joined) and denies the call, rule `isolation-not-active`, unless: the four flags have the block's values, every generated `denyRead` entry is present, `allowRead` holds nothing else, and the `sandbox` object holds no key outside a closed list (the block's own keys, `filesystem.denyWrite` and `network.deniedDomains`, which only narrow). A closed list, not a list of weakening keys, so a setting that a later Claude Code adds cannot slip past. `filesystem.allowWrite` and `network.allowedDomains` are outside the list: a project file could ship either one. Outside `sandbox` no closed list is possible, so the check covers exactly the project settings that the Claude Code docs name as sandbox write or host sources (`_grants`): any `permissions.additionalDirectories`, any `Edit` entry in `permissions.allow`, and any `WebFetch(domain:...)` entry in `permissions.allow`, which the docs add to the same host list as `allowedDomains` (the text before the first `(` is the tool name, so no path or host is matched; a bare `WebFetch` rule adds no host and passes). A new source in the docs is a new row there. Extra write folders and trusted hosts belong in the user's own settings, which Pre cannot see. An unreadable file, invalid JSON or an exception is a deny, never an ask: an unchecked shell call is what the layer exists to stop. An empty file counts as no file, because the sandbox leaves a zero-byte placeholder for `.claude/settings.json` while a command runs and a parallel call's Pre can see it (seen in the live run on 2026-11-06). It is a check for user mistakes, not a barrier: the hook input carries no sandbox state, and Pre cannot see managed settings, a `--settings` flag, `--setting-sources`, `--add-dir` or a user settings file.
- **The link check** (`rules.match` with `cwd`). With isolation on, the resolved form of each path field of a non-Bash tool is also matched against the path rules, where a link was followed. This closes the two-call bypass: `ln -s .e""nv link` in Bash, then `Read ./link`. The resolved form is matched like any other: a rule with `project_relative` (only `deny-prod-config`) sees a path that resolves inside the project (`CLAUDE_PROJECT_DIR`, else the hook's working folder) as the part below the project folder, so a project under a folder named `production` is not denied. That inside test is by text (`~` expanded, joined to the working folder, cleaned, compared with a `/` boundary against the project folder as written and as resolved); links are followed only here, on the named path fields. The text spelling and the resolved form are separate entries and each places itself, so a link then `..` out of the project is matched whole on its cleaned text spelling, and a link inside the project named `production` is denied like a folder of that name. Every other string (Bash words, MCP strings) is placed by text with no disk call, so large input costs only the text work. With isolation off no link is followed, so a link out is allowed there; in a project under a `prod` folder that is weaker than before the rule, which denied the whole path. With isolation on the check only adds denies to what the text spelling gets. Bash is left to the sandbox, which blocks a link to a listed file.
- **Post redaction** (`redact.redact_fields`). Covered in "What happens on one tool call". It is a second check for shaped secrets that the masks do not cover (environment variables, files outside the project), not the control. It reverses the stance "the conversation is never changed", for isolation only.

What the layer does not do is under "What isolation does not stop" below and in THREAT_MODEL ("Isolation (opt-in)" under "Gaps in the rules"). Tested: `tests/unit/test_t014_isolation.py` and the T-014 cases of `tests/e2e/test_hooks_e2e.py` (the plugin's code, on real files), and `tests/live/t014_probe.py` (real `claude -p` sessions with the real sandbox; run by hand after a Claude Code upgrade). On a host with Ubuntu's user-namespace restriction and no AppArmor profile the exact block refuses every shell command (the script shows it, then uses a probe-only `network.allowAllUnixSockets` override in a `--settings` file to show the masks; the shipped block never sets it, and the tripwire denies it in a project file). Not probed: PowerShell and Monitor (the docs say they are sandboxed), macOS, a host with no bubblewrap beyond the start-up refusal, git worktrees.

### Isolation from the user's side

The rules match text, so a shell command that never spells a secret file's name gets past them (`cat .e""nv`, `cat .n*rc`, `cd ~/.kube && cat config`). More matching cannot close that: the shell has no end of spellings. Isolation closes it with Claude Code's own Bash sandbox instead. It is **off by default**. With it on:
- The plugin ships a settings block for the sandbox (`isolation/settings.local.json` in the plugin folder). It is generated from the secret rules of `policy.json` (`make isolation`), and a test fails while the committed file is stale. The sandbox then hides the listed files from every Bash, PowerShell and Monitor command: anywhere in the project folder, and directly in `~` and `~/.config`. A hidden file gives `Permission denied`, a hidden folder shows as empty.
- Pre denies every shell call (rule `isolation-not-active`) when the block is not in the project's `.claude/settings.json` or `.claude/settings.local.json`, and the reason names the failing setting and both files, and says to remove it or to merge the block's `sandbox` key. It also denies a project setting that lets a sandboxed command write outside the project or reach new hosts: `sandbox.filesystem.allowWrite`, `permissions.additionalDirectories`, `sandbox.network.allowedDomains`, a `WebFetch(domain:...)` allow rule (Claude Code adds those hosts to the same list) or an `Edit(...)` allow rule in `permissions.allow`. This is a check for mistakes, not a barrier: it cannot see managed settings, a `--settings` flag, `--add-dir` or your user settings.
- Pre denies a file tool (Read, Edit, Write and the like) that opens a listed file through a symbolic link, which the sandbox cannot see.
- Post replaces secrets with a known shape (the seven formats of control 5) in the output of a shell command that succeeded, before Claude sees it. This is the one place the plugin changes what Claude sees.

#### Turn it on

1. Copy `isolation/settings.local.json` from the plugin folder into each project's `.claude/settings.local.json`, or merge its `sandbox` key into the file you have. Do not loosen it: Pre denies a block with an entry removed, an extra `allowRead` entry, `excludedCommands`, `network.allowAllUnixSockets`, or any key it does not know, and it denies `allowWrite`, `permissions.additionalDirectories`, `sandbox.network.allowedDomains`, `WebFetch(domain:...)` allow rules and `Edit(...)` allow rules in the project's settings files. Put extra write folders and trusted hosts in your user settings (`~/.claude/settings.json`). They then apply to every project, and Pre cannot see them. If you answer "Yes, and don't ask again" to a network prompt, Claude Code saves a `WebFetch(domain:...)` allow rule to the project's `.claude/settings.local.json`, and Pre then denies every shell call until you move that rule into your user settings.
2. Write `{"version": 1, "isolation": true}` to `${CLAUDE_PLUGIN_DATA}/policy.json` (or to the file `GUARDRAILS_POLICY` names). A `true` in any policy file turns it on, and no file can turn it off again. Claude cannot write these files for you.
3. Start Claude Code in the project folder (not in `~` or `/`: the block's `./**/` entries would then cover your whole home folder, and each command took 100 to 187 seconds on a 4.5-million-file home folder). Do not start it from an activated project virtual environment (limit 7 in [THREAT_MODEL](THREAT_MODEL.md)).
4. On Ubuntu with `kernel.apparmor_restrict_unprivileged_userns` set to 1, the sandbox cannot start until you add Anthropic's AppArmor profile for `/usr/bin/bwrap` once (a root step; the text is in the Claude Code sandboxing docs, "Add an AppArmor profile for bubblewrap"): `sudo tee /etc/apparmor.d/bwrap`, then `sudo systemctl reload apparmor`. Until then every shell command is refused, with `apply-seccomp: write /proc/self/setgroups` in the error, and nothing runs unsandboxed (the block sets `failIfUnavailable` and turns the unsandboxed retry off). The plugin has no fallback wrapper.
5. Restart Claude Code and run `/sandbox` to confirm the sandbox works.

#### Why isolation stays opt-in

- `ssh` and git over ssh stop working: `~/.ssh` is hidden and plain `ssh` has no route out of the sandbox.
- `git push` over https with stored credentials stops working. Pushing over https works if the token is in an environment variable and a credential helper reads it (`GH_TOKEN` and `credential.helper=!f() { echo username=x-access-token; echo password=$GH_TOKEN; }; f`); otherwise push from your own terminal. The plugin already asks before every push.
- Tools that read `~/.ssh` or a hidden `.npmrc` fail (`~/.ssh/*.pub` and `known_hosts` too). A Python virtual environment named `.env` is hidden whole (not tested).
- It needs bubblewrap and user namespaces. On Ubuntu with the restriction it needs the one-time root step above.
- The first connection to each new network host asks. In auto mode Claude Code refuses it unless the classifier approves, and in dontAsk mode it refuses it. A host listed in `sandbox.network.allowedDomains` of your user settings, or named in a `WebFetch(domain:...)` allow rule there, passes without a question.
- Each shell command takes about 0.15 to 1.3 seconds longer, by project size (measured on a probe project and on one of 272,000 files).
- Each project needs its own copy of the block, a new git worktree has none (its shell calls are denied until you copy it; not tested), and a plugin update that adds a name to the secret list makes every copy stale.
- Writes outside the project and the temp folder are denied.

#### What isolation does not stop

Accepted limits, each tested at its stated result (the rest are rows of the table in "What holds each threat" in [THREAT_MODEL.md](THREAT_MODEL.md#what-holds-each-threat)):
- `deny-key-files` (`*.pem`, `*.key`) is not in the block: a mask on every `*.pem` would hide the certificate bundle that Python's `certifi` ships inside a project virtual environment. A key file outside `~/.ssh` is readable by the shell, and Pre only asks about it.
- Output of a command that fails comes back unredacted (Claude Code gives the plugin no way to change it), and so does output that is saved to a file because it is large, or that comes from a background command.
- Matching ignores case in Pre; the sandbox does not, so `.ENV` is not hidden.
- Tool config overrides (`XDG_CONFIG_HOME`, `GH_CONFIG_DIR`, `AWS_SHARED_CREDENTIALS_FILE`, `KUBECONFIG`, `DOCKER_CONFIG`, `CLOUDSDK_CONFIG`) move credential files, and `--add-dir` folders are not under the project folder. Claude Code's own token file, `~/.claude/.credentials.json`, can be read by a sandboxed command.
- In bypass mode the agent can edit `.claude/settings.local.json` with the Edit tool; an edit that loosens the block trips the check on the next shell call, but an edit through a scope Pre cannot see does not.
- Code that runs outside the sandbox (a project hook, an `.mcp.json` server) can run files that a sandboxed command wrote.
- A secret file created while a shell command is already running can be read by that command: Claude Code (2.1.319, Linux) turns each sandbox `denyRead` pattern into the list of matching files when each command starts, and the next command hides the new file. A file pattern (`.env*`, `.npmrc`) leaks when the file is late. A folder pattern (`~/.aws`) still hides a late file inside a folder that existed at the start, but leaks when the folder itself is made late. No setting re-scans; the fix is in Claude Code (tested 4 of 4 each way).

Stronger options, not shipped: `sandbox.credentials.envVars` deny entries (hide named environment variables; each variable must be named), `permissions.blockReadsOutsideWorkingDirectories` (closes the folder-outside-the-project row; breaks tools that read home config such as `~/.cargo`), and an admin-required sandbox in managed settings (`allowUnsandboxedCommands: false` there makes Claude Code ignore repository settings that loosen it).

#### Tested on

The probe sessions behind this layer ran on Claude Code 2.1.318 (2026-11-05) and `tests/live/t014_probe.py` on 2.1.319 (2026-11-06), on Linux, with fake secrets and the plugin loaded with `--plugin-dir`. Run `python3 tests/live/t014_probe.py` (it needs the `claude` CLI signed in; it starts several short `claude -p` sessions, which cost a few cents) after you upgrade Claude Code: the block relies on behaviour seen on those versions (`./` anchoring, the Linux wildcard rule, `failIfUnavailable`), and the plugin does not check the version. On a host with the Ubuntu restriction and no profile, the script shows the exact block refusing every shell command, then uses a probe-only override (`network.allowAllUnixSockets` in a `--settings` file, which skips the seccomp step) to show the masks. The shipped block never sets that override, and Pre denies a shell call when a project settings file sets it. PowerShell and Monitor are sandboxed per the Claude Code docs; they were not run.

## Audit and state

- Audit: `${CLAUDE_PLUGIN_DATA}/audit/YYYY-MM-DD.jsonl` (the plugin creates the folders with mode 0700 and the files with mode 0600; an existing folder or file keeps its mode). Each line is written with one `write` call on an append-mode file, which is meant to keep two hooks running at once from mixing lines. This is expected on a local file system and has not been tested with real parallel hooks; the return value of `os.write` is not checked. A short write would leave a partial line. Each line is one JSON object with: `ts` (UTC time), `session_id`, `tool_name`, `tool_use_id`, `event` (`decision` or `result`), `decision`, `rule`, `step`, and `input` (redacted; if longer than `audit.max_input_chars`, default 2000, it is replaced by `{"truncated": "<the first max_input_chars characters of the input as JSON text>"}`). Decision lines also have `reason`. Decision lines also have `tainted` (true or false from Pre's read of the session mark, `null` when it could not be read). Result lines also have `warned` (true when a note was sent to Claude for this result; lines from before the note have none), `tainted` (the mark after this call) and `result_bytes`, `status` (`error` for a PostToolUseFailure event, or when the tool response has `is_error` or `interrupted` set to a true value, otherwise `ok`) and `warnings` (a list; each entry is `{"warning": "prompt-injection-suspected", "marker": <marker id>, "excerpt": <text from the scanned string, redacted, at most 80 characters>}`, or `{"warning": "scan-timeout", "marker": <id of the marker that was running, or null>}`). A result line has `scan_truncated: true` only when the 200000-character cap cut text. `result_bytes` is the UTF-8 size of the response as JSON text. Every line is written with `ensure_ascii`, so it is ASCII: a non-ASCII character appears as `\uXXXX` (`jq` and `json.loads` show the original; `grep` for a non-ASCII word in the raw file does not find it), and a lone surrogate cannot stop the write. Unless `otel_field_names` is false, three more fields are added: `gen_ai.tool.name`, `gen_ai.tool.call.id` and `gen_ai.conversation.id`.
- State: `${CLAUDE_PLUGIN_DATA}/state/<session>.calls`, `<session>.decisions` (the "memo") and `<session>.taint` (the session mark: one line `{"id", "tool", "markers", "ts", "agent", "input", "excerpts"}` per flagged outside-content result, redacted and cut like a log line, so the dashboard can show what marked the session; Pre reads only its size, and a missing file means unmarked). `<session>` is the session id with every character other than letters, digits, `_` and `-` replaced by `_` (so `a/b` and `a_b` share files), cut to 80 characters. `.calls` gets one line `{"id": <tool_use_id>}` per call, and the step number is the number of lines. `.decisions` gets one line per call with the fields `id`, `decision`, `rule` and `step`; Post uses the last line whose `id` matches. Pre and Post are separate processes, and these files are how Post learns Pre's decision.
- Known limit: the step counter is not locked. Two parallel calls can get the same number. A lock is not built.
- Known limit: each Pre call reads the session's whole `.calls` file (to count it) and each Post call reads the whole `.decisions` file (to find its line), so the work per call grows with the length of the session. This was not measured. The shared `unknown.calls` and `None.calls` files grow without bound. Cleanup is not built: delete old state files by hand.
- Known limit: if Claude Code sends no `session_id`, every call counts in one shared file, `unknown.calls`, which, like every state file, is never cleaned up (a normal session has its own file, so only the shared files, this one and `None.calls` for a `null` id, carry over between sessions). After 200 calls in total, across all sessions and days, every call with no other rule gets `ask` (the step cap). If it sends no `tool_use_id`, Post cannot tell calls apart and takes the last decision with a null id, which may belong to a different call, so a result line can show the wrong decision.
- Known gap: Pre writes a log line only when it denies or asks. For an allowed call it writes only the memo in `state/<session>.decisions`, so the first log line of an allowed call is the result line that Post writes after the call. An allowed call that never ran, or whose Post script failed, leaves nothing in the log. A failed tool call goes to a separate event, PostToolUseFailure (its input has `error` and no `tool_response`; read from the Claude Code 2.1.318 binary). `hooks.json` registers the Post script for both events, so a failed call gets a result line with `status` `error`. A change that is possible but not made: write a decision line for every call and let Post read it from the log instead of from the memo. That would close this gap. The price is one more log line for every allowed call, and a search of the day's log file (one file per day, shared by all sessions) in place of a small per-session memo. The step counter file would stay.

### Audit log format

- Path: `${CLAUDE_PLUGIN_DATA}/audit/YYYY-MM-DD.jsonl` (UTC date). Folder mode 0700, file mode 0600 when the plugin creates them (an existing folder or file keeps its mode). `${CLAUDE_PLUGIN_DATA}` is the data folder: Claude Code sets this variable for plugin hooks, it is outside the plugin folder and it survives plugin updates (as Claude Code documents it; not tested here). The plugin keeps its log (`audit/`) and counters (`state/`) there. Claude Code picks the folder. For plugins installed from a marketplace, the data folders on one Linux machine were under `~/.claude/plugins/data/<plugin>-<marketplace>/`.
- `event: "decision"` lines come from the PreToolUse hook. Only deny and ask are written there. They carry `tainted`: true when the session was marked at that call, false when it was not, `null` when the mark could not be read.
- `event: "result"` lines come from the PostToolUse hook, and from the PostToolUseFailure hook for a call that failed (`status` is `error`), for every call that ran when the Post script works (if it fails, the call leaves no result line). They carry the decision, rule and step that PreToolUse recorded. A result line has `scan_truncated: true` when the result was longer than 200000 characters and the rest was not scanned, and a `scan-timeout` warning when a marker did not finish in 3 seconds. They also carry `warned` (true when a note was sent to Claude for that result; lines written before the note existed have warnings but no `warned`) and `tainted` (the session is marked after this call; `null` when the mark could not be read).
- Secrets in the input are replaced with `[REDACTED:<kind>]` before writing and before the 2000-character cut below. Kinds: private-key, anthropic-key, openai-key, aws-access-key, aws-secret-key, github-token, bearer-token.
- If the JSON text of the input is longer than 2000 characters (the default of `audit.max_input_chars` in `policy.json`), the whole `input` field is replaced by `{"truncated": "<the first 2000 characters>"}`.
- Every line is plain ASCII: a non-ASCII character is written as `\uXXXX`. `jq` and `json.loads` show the original text; `grep` for a non-ASCII word in the raw file does not find it.
- `agent` names the agent that made the call: `claude-code` (also when the hook input does not say), `cursor`, `codex`, the name a generic caller gave, `mcp-proxy`, `shell`, or `dashboard`.
- The shell wrapper writes the `result` line of an allowed command before the command runs, with `status: "started"`: nothing of the wrapper is left once the real shell has taken over.
- `event: "mark-cleared"` is written when a person clears a session mark from the dashboard.
- Field names `gen_ai.tool.name`, `gen_ai.tool.call.id` and `gen_ai.conversation.id` follow the OpenTelemetry GenAI naming style. There is no exporter. Setting `audit.otel_field_names` to false in `policy.json` leaves the three fields out.

### Set aside, one line each

The table above has the reasons. An allowlist would block every command not listed. A deny on every internal error would stop all work, so an error asks. Blocking injected text has false positives, and rewriting it makes the model see text that differs from the tool's real output, so it is scanned, Claude is told, and a hit from an outside source marks the session. Claude Code's own `permissions.deny` and sandbox show no per-rule reason and are not known to keep a per-call decision log (not checked), and they can be used together with this plugin. Isolation (a container or a separate account) is the stronger control for what the rules cannot see, and was not weighed against this plugin; this plugin has an opt-in layer for shell reads of secret files, built on Claude Code's own sandbox (see "Isolation (opt-in)"). A user's policy file is merged into the shipped policy and can only add (one exception: `trusted_tools`, see "Change the rules"): a file that could replace or loosen the shipped rules would let the agent switch the guard off (a full copy that replaced the shipped policy was the old design). `pip` for the engine would need a package-manager step that a plugin install is not expected to run, and a venv is not portable between machines, so the engine is copied in. A small shell tokeniser in place of the regexes was not tried (it would catch quoted flags; see "More limits" in [THREAT_MODEL](THREAT_MODEL.md#more-limits)). The step is counted after the rules, so a deny stays a deny when the counter cannot be written. A built-in minimum deny list for a broken shipped policy is not built.

| Windows, Python 3.8, Claude Code before 2.1.295 | Untested; no version check | "Known gaps" |

## Cuts (things not built) and known gaps

### Cuts

- **No spend cap.** A hook input has no cost field. A cap estimated from the session transcript (its path is in the hook input) was not attempted.
- **No injection blocking or rewriting.** A phrase match has false positives, and rewriting tool output means the model sees text that differs from the tool's real output, which the log would not show. The scan tells Claude and the person, and marks the session when the tool reads outside content; it never edits or hides the result. It is a signal, not a shield.
- **No OpenTelemetry exporter.** The log uses OpenTelemetry's field names (`gen_ai.tool.name` and two more) so an exporter could read it later. Nothing is sent anywhere.
- **One static dashboard page; a server only when you start it.** The repo ships `index.html`, a single self-contained static dashboard page with no runtime dependencies. It asks for `/api/status`, `/api/policy` and `/api/events` and shows the policy and the audit log from them; if those do not answer (for example when you open the file by double-click), it says it is not connected and shows no sample data. If a server that was answering stops, it says so, keeps the rows it has and keeps trying. `packages/guardrails-dashboard` serves the page and `/api` on demand, on 127.0.0.1 only, and only to a request that carries the one-time key it prints at start. Every GET only reads (`/api/inventory` is the discovery scan). The one POST, `/api/taint/clear`, deletes the mark file of one session and writes a `mark-cleared` log line; a request from another site's page is refused. From a clone, `make dashboard` starts it. A plugin install carries a copy of the server and the page (see "Decision: dashboard in the plugin") and `dashboard.py` starts it, but it runs only when you start it, and the hooks open no port. The log itself stays a JSONL file you can `grep` and `jq`.

### Known gaps

This subsection lists known gaps, not design choices: a fix is possible and not built, or the thing was not tested.

- **No check of the Claude Code version.** `onFailure` needs 2.1.295 or later. The plugin does not test for it, so a user on an older version gets no warning that the hard fail-safe is missing. No work item is recorded for this.
- **No log or state cleanup or rotation.** One log file per day, one pair of state files per session. Delete old files yourself.
- **No file lock for the counter.** See above.
- **No Windows testing.** No Windows machine was used. The path globs that contain `/` (`*/.ssh/*`, `*/prod/*`, `*/.aws/*`) are not expected to match Windows paths with backslashes; the file-name globs (`.env*`, `*.pem`) may still match. `hooks.json` runs `python3`, which may be missing on Windows: then Pre cannot start (the call should be blocked on 2.1.295 or later, untested; on older versions nothing is checked). CI runs on Linux only.
- **No tests on Python 3.8.** The plugin folder and core are written for Python 3.8 or newer, but only 3.12 and 3.14 were run by hand (the hook scripts and the tests), and CI uses the runner's stock `python3`, whose version is not recorded. The workspace root and the demo need Python 3.9 or newer to run the tests and the demo. The unit tests run under the interpreter of `uv run pytest`; only the hook subprocesses use the runner's stock `python3`.
